# Implementation Plan: Migrate to vault_kv_secret_v2 Ephemeral Resource

## 1. Problem Analysis

### Current State
- Using deprecated `data.vault_kv_secret_v2` data source for fetching secrets from Vault
- This data source materializes secrets into Terraform state files, creating a security risk
- Atlantis CI logs show 4+ deprecation warnings across the codebase
- The deprecated data source is used to fetch secrets that are then passed to `forgejo_organization_action_secret` resources

### Root Cause
The Vault Terraform provider deprecated the `data.vault_kv_secret_v2` data source in favor of `ephemeral.vault_kv_secret_v2`, which:
- Does not persist secrets in state files
- Uses Terraform 1.10+ ephemeral values feature
- Provides better security guarantees for secret handling

### Blocker Identified
Per the note from Claude in the issue:
> "The clean fix, ephemeral read plus a write-only data_wo on the forgejo resource, isn't available until the forgejo provider adds write-only support for action-secret data."

The Forgejo provider currently lacks write-only attribute support for `forgejo_organization_action_secret.value`, meaning:
- Ephemeral values from Vault cannot be directly passed without state materialization
- Need a workaround until upstream provider is updated

### Why This Matters
1. **Security**: Secrets currently leak into state files
2. **Compliance**: Deprecated resources may lose support
3. **Best Practice**: Ephemeral values are the recommended pattern for secret management in Terraform 1.10+

## 2. Technical Approach

### Strategy
Use **ephemeral resource + lifecycle ignore_changes workaround** until Forgejo provider gains native write-only support.

### Migration Path
1. Replace `data.vault_kv_secret_v2` with `ephemeral.vault_kv_secret_v2`
2. Pass ephemeral values to `forgejo_organization_action_secret.value`
3. Add `lifecycle { ignore_changes = [value] }` to prevent state tracking of secret values
4. Document the workaround and track upstream issue

### Alternative Approaches Considered
- **Wait for Forgejo provider update**: Delays fix, security risk persists
- **Use external secret injection**: Adds complexity, breaks IaC patterns
- **Switch to different secret store**: Too invasive, not addressing root cause
- **Chosen approach**: Pragmatic workaround that improves security now while maintaining functionality

### Prerequisites
- Terraform >= 1.10.0 (ephemeral resource support)
- Vault provider >= 4.5.0 (ephemeral resource availability)
- Forgejo provider (current version, no changes needed)

## 3. Implementation Steps

### Step 1: Verify Provider Versions
1. Check `versions.tf` or provider configuration
2. Ensure Terraform version constraint includes `>= 1.10.0`
3. Ensure Vault provider version is `>= 4.5.0`
4. Document current Forgejo provider version for future reference

### Step 2: Identify All Deprecated Data Sources
1. Search codebase for `data "vault_kv_secret_v2"`
2. List all resources consuming these data sources
3. Map dependencies: vault secret → forgejo resource → actual usage
4. Expected findings based on logs:
   - `data.vault_kv_secret_v2.cachix`
   - 3+ additional similar data sources

### Step 3: Create Migration Template
1. Convert one data source as proof-of-concept
2. Pattern:
   ```hcl
   # OLD
   data "vault_kv_secret_v2" "cachix" {
     mount = "secret"
     name  = "cachix"
   }
   
   # NEW
   ephemeral "vault_kv_secret_v2" "cachix" {
     mount = "secret"
     name  = "cachix"
   }
   ```
3. Update resource references:
   ```hcl
   # OLD
   resource "forgejo_organization_action_secret" "cachix_auth_token" {
     organization_id = data.forgejo_organization.this.id
     secret_name     = "CACHIX_AUTH_TOKEN"
     value           = data.vault_kv_secret_v2.cachix.data["auth_token"]
   }
   
   # NEW
   resource "forgejo_organization_action_secret" "cachix_auth_token" {
     organization_id = data.forgejo_organization.this.id
     secret_name     = "CACHIX_AUTH_TOKEN"
     value           = ephemeral.vault_kv_secret_v2.cachix.data["auth_token"]
     
     lifecycle {
       ignore_changes = [value]  # ponytail: workaround until forgejo provider adds write_only support
     }
   }
   ```

### Step 4: Apply Migration to All Data Sources
1. Repeat pattern for each `vault_kv_secret_v2` data source
2. Update all downstream resource references
3. Add lifecycle blocks to all `forgejo_organization_action_secret` resources

### Step 5: Add Documentation
1. Add inline comment explaining the `ignore_changes` workaround
2. Create or update `TERRAFORM.md` with:
   - Why ephemeral resources are used
   - Why `ignore_changes` is necessary
   - Link to Forgejo provider issue (create if doesn't exist)
   - Removal criteria: "Remove lifecycle block when forgejo provider supports `sensitive = true` or `write_only = true` on action secret values"

### Step 6: Validate Changes
1. Run `terraform fmt`
2. Run `terraform validate`
3. Run `terraform plan` in non-production environment
4. Verify:
   - No recreation of resources
   - Warnings are resolved
   - Secrets still flow correctly

### Step 7: Deploy and Monitor
1. Apply in staging/test environment first
2. Verify action secrets still work in Forgejo
3. Apply to production
4. Monitor Atlantis logs for warnings

## 6. Risks

### High Risk
- **State corruption**: Changing resource types mid-flight can confuse Terraform
  - **Mitigation**: Use `terraform plan` extensively, test in staging first
  - **Likelihood**: Low (we're changing data source type, not resource)

- **Secret unavailability**: If ephemeral resources fail to read from Vault
  - **Mitigation**: Verify Vault connectivity and permissions before migration
  - **Likelihood**: Low (uses same authentication)

### Medium Risk
- **Forgejo provider compatibility**: Ephemeral values may not work as expected
  - **Mitigation**: The `ignore_changes` workaround handles this
  - **Likelihood**: Medium (this is why we need the workaround)

- **Terraform version incompatibility**: CI/CD may use older Terraform
  - **Mitigation**: Check Atlantis/CI Terraform version before starting
  - **Likelihood**: Low (ephemeral support is in 1.10+)

### Low Risk
- **Downstream consumers break**: Other resources depending on secret data
  - **Mitigation**: Map all dependencies in Step 2
  - **Likelihood**: Low (secrets are leaf resources)

### Blockers
- **Forgejo provider lacks write_only support**: Known limitation
  - **Status**: Acknowledged in issue, workaround planned
  - **Workaround**: `lifecycle { ignore_changes = [value] }`
  - **Long-term**: Track upstream provider issue, remove workaround when fixed

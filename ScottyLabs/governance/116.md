# Implementation Plan: Disable Pull Requests on GitHub Mirrors

## 1. Problem Analysis

### What needs to be solved
The credit-conserver bot currently creates pull requests on all configured target repositories without checking if the repository is a mirror. GitHub mirrors are read-only copies of repositories from other sources (e.g., GitLab, Bitbucket, or other GitHub repos), and creating PRs on them is inappropriate because:

1. **Mirrors are read-only by design** - Changes should go to the source repository, not the mirror
2. **PRs on mirrors create confusion** - Contributors don't know where to submit changes
3. **Wasted API credits** - The bot consumes Anthropic API credits generating plans for repos that can't accept PRs
4. **Cluttered mirror repos** - Automated PRs pollute repositories that are meant to be pristine copies

### Why this matters
The bot needs to respect repository configuration and skip PR creation on mirrors to:
- Conserve API credits for repositories that can actually accept contributions
- Avoid creating noise in mirror repositories
- Maintain clean separation between source and mirror repositories

### Dependency
The solution depends on https://github.com/integrations/terraform-provider-github/pull/3479, which likely adds support for detecting or configuring the `has_pull_requests` repository property via the GitHub Terraform provider.

## 2. Technical Approach

### Strategy
Add a repository validation step that checks if a repository allows pull requests before processing issues. GitHub repositories have a `has_issues` and potentially a `has_pull_requests` flag (once the terraform provider PR is merged) that indicates whether the feature is enabled.

### Key Decisions

1. **Check repository properties at workflow start**: Before processing any issues from a repository, query the repository metadata to determine if PRs are enabled
2. **Skip vs. warn approach**: Log a warning and skip the repository entirely if PRs are disabled, rather than processing issues without creating PRs
3. **Platform-specific implementation**: Add the check to the `GitPlatform` interface so both GitHub and Codeberg implementations can support it
4. **Fail-safe default**: If the property check fails or is unavailable, assume PRs are enabled (backward compatible)

### Alternative Considered
- **Config-based exclusion**: Add a manual exclude list in `config.yml` for mirror repos
  - **Rejected**: Requires manual maintenance and doesn't scale; better to detect automatically

## 3. Implementation Steps

1. **Add `has_pull_requests` check method to GitPlatform interface**
   - Define abstract method `supports_pull_requests(repo) -> bool`
   - Returns True if repository accepts PRs, False otherwise

2. **Implement check in GitHubPlatform**
   - Use PyGithub to check `repo.has_issues` and any available PR-related flag
   - Note: May need to wait for terraform provider PR to expose `has_pull_requests`
   - Fallback: Check if repo is a mirror/fork or has PRs disabled via API

3. **Implement check in CodebergPlatform**
   - Use Gitea API to check repository settings
   - Gitea has `has_pull_requests` in repository JSON response

4. **Add validation in parallel_workflow_runner.py**
   - Before calling `_process_single_issue()`, check `platform.supports_pull_requests(repo)`
   - Log warning and skip repository if PRs are disabled
   - Update metrics/summary to track skipped repositories

5. **Add configuration option**
   - Add `skip_mirror_repos: true` to `config.yml` workflow section
   - Allow users to disable this check if needed

6. **Update logging and reporting**
   - Log clear message when skipping a mirror: `"[GitHub] Skipping owner/repo: Pull requests are disabled (mirror repository)"`
   - Include skipped repo count in final summary

7. **Add tests**
   - Mock repository with `has_pull_requests: false`
   - Verify workflow skips the repo
   - Verify no API calls are made for plan generation

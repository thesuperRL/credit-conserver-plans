# Implementation Plan: Restore Governance Visualizer

## 1. Problem Analysis

### What needs to be solved
The credit-conserver system currently processes GitHub/Codeberg issues and generates implementation plans, but lacks a visualization dashboard to monitor:
- Which issues have been triaged and planned
- Credit usage patterns across repositories
- Processing status and workflow health
- Historical activity on governance-related repositories (particularly ScottyLabs/governance)

### Why this is needed
Without a visualizer, users must:
- Manually check GitHub Actions logs for bot activity
- Navigate to each target repository to see generated PRs
- Lack visibility into credit consumption patterns
- Cannot easily see the bot's impact on the governance repository

A governance visualizer would provide:
- **Centralized monitoring**: Single dashboard for all bot activity
- **Transparency**: Clear view of what the bot has processed
- **Credit tracking**: Visual representation of budget usage
- **Governance oversight**: Specific focus on the governance repository workflow

## 2. Technical Approach

### Strategy
Build a lightweight, static HTML dashboard that:
1. **Reads from existing GitHub/Codeberg APIs** (no new data storage)
2. **Generates static HTML reports** that can be committed to the plans repository
3. **Uses client-side JavaScript** to fetch live data from public APIs
4. **Requires zero infrastructure** beyond existing GitHub Pages

### Key Decisions

**Decision 1: Static HTML + Client-Side JS over Backend Server**
- **Rationale**: Ponytail principle - no need for server infrastructure when browser can fetch public APIs directly
- **Trade-off**: Limited to public repository data unless user provides PAT in browser

**Decision 2: Generate dashboard as part of workflow, commit to plans repo**
- **Rationale**: Reuse existing git infrastructure; GitHub Pages renders it automatically
- **Trade-off**: Dashboard updates only when workflow runs (acceptable for 6-hour cron)

**Decision 3: Focus on governance repo first, extensible to all repos**
- **Rationale**: Issue mentions "governance visualizer" specifically
- **Trade-off**: Initial scope is narrow, but architecture allows expansion

**Decision 4: Single HTML file with embedded CSS/JS**
- **Rationale**: Simplest deployment, no build step, works offline after first load
- **Trade-off**: Larger initial page load, but overall size will be <100KB

## 4. Files to Modify

### New Files

**`modules/visualizer.py`**
- Function: `generate_dashboard_html(summary: dict, history: list) -> str`
- Renders HTML template with:
  - Summary statistics embedded as JSON
  - Chart.js visualizations for credit usage
  - Responsive table for repository activity
  - Filter/search capabilities

**`templates/dashboard.html`** (or embed as string in visualizer.py)
- Single-page application structure
- Sections: Header, Stats Cards, Charts, Tables, Footer
- Minimal CSS (Tailwind via CDN or simple custom styles)
- Chart.js for credit usage line chart
- Client-side filtering and search

### Modified Files

**`modules/parallel_workflow_runner.py`**
- Modify `_generate_summary()` to include:
  - `processed_issues`: List of {repo, issue_number, title, pr_url, timestamp}
  - `credit_timeline`: List of {timestamp, tokens_used, tokens_remaining}
  - `repo_stats`: Per-repo breakdown with success/failure counts
- Store summary history in memory (or read from previous runs if persisted)

**`main.py`**
- After `workflow.run()`, call:
  ```python
  from modules.visualizer import generate_dashboard_html
  html = generate_dashboard_html(summary, [summary])  # history of 1 for now
  Path("dashboard.html").write_text(html)
  ```
- Only generate dashboard if `GENERATE_DASHBOARD=true` env var set

**`plans_agent.py`**
- After processing all issues, commit dashboard.html to plans repo:
  ```python
  if Path("dashboard.html").exists():
      shutil.copy("dashboard.html", PLANS_LOCAL_DIR / "dashboard.html")
      # git add, commit, push
  ```

**`config.yml`**
- Add new section:
  ```yaml
  visualization:
    enabled: true
    dashboard_path: "dashboard.html"
    include_charts: true
  ```

**`README.md`**
- Add section "Governance Dashboard" with link to GitHub Pages URL
- Explain what metrics are displayed
- Document how to disable dashboard generation

## 6. Risks & Unknowns

### Risk 1: GitHub Pages may be disabled on plans repo
- **Impact**: Dashboard won't be publicly accessible
- **Mitigation**: Document alternative hosting (Netlify, Vercel, local file)
- **Fallback**: Generate dashboard locally only, view as file://

### Risk 2: Chart.js CDN unavailable
- **Impact**: Visualizations won't render
- **Mitigation**: Include fallback to pure HTML tables
- **Detection**: Add error handling for script load failures

### Risk 3: Summary data structure changes over time
- **Impact**: Dashboard breaks when reading old summary formats
- **Mitigation**: Version summary data (e.g., `version: "1.0"` field)
- **Handling**: Dashboard displays error message for unsupported versions

### Risk 4: Performance with large datasets
- **Impact**: Dashboard slow to render with 1000s of issues
- **Mitigation**: Limit history to last 100 runs, paginate tables
- **Alternative**: Generate separate monthly archive dashboards

### Unknown 1: Desired metrics for "governance" specifically
- **Question**: What governance-specific metrics are needed beyond general bot activity?
- **Resolution**: Start with basic metrics (issues processed, PR creation rate), gather feedback
- **Follow-up**: Add governance-specific sections based on ScottyLabs team input

### Unknown 2: Historical data availability
- **Question**: Should dashboard show data from before visualizer was added?
- **Resolution**: Phase 1 shows only data from current run forward
- **Enhancement**: Phase 2 could parse old GitHub Actions logs to backfill history

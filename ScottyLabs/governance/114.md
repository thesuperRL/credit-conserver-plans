# Implementation Plan: Add Agit Support to Atlantis

## 1. Problem Analysis

### What Needs to Be Solved
Atlantis currently supports GitHub, GitLab, Bitbucket, and Azure DevOps as VCS providers, but lacks support for agit-based workflows commonly used in Gitea and Forgejo instances. Agit is a git extension that enables creating pull requests directly through git push commands without requiring a web interface.

### Why It's Needed
- **Gitea/Forgejo adoption**: Many organizations self-host Gitea/Forgejo and use agit workflows
- **CLI-first workflow**: agit enables PR creation via `git push origin HEAD:refs/for/main`, aligning with terminal-centric development
- **Atlantis gap**: Atlantis already supports Gitea/Forgejo but doesn't handle agit-style PR creation and updates
- **Upstream contribution**: Adding this to Atlantis benefits the entire community

### Current State
- Atlantis has a Gitea VCS provider (`server/vcs/gitea_client.go`)
- The Gitea client likely uses standard PR APIs
- Agit PRs are created via special git refs (`refs/for/<branch>`) but appear as normal PRs in the API
- The integration gap is in detecting and handling agit-specific events and ref patterns

## 2. Technical Approach

### Strategy
1. **Extend Gitea VCS client** to recognize agit ref patterns
2. **Webhook handling** for agit push events
3. **PR detection logic** to identify agit-created PRs
4. **Event normalization** to treat agit PRs consistently with web-created PRs
5. **Documentation** for setup and configuration

### Key Decisions
- **Minimal invasive changes**: Keep agit support within the existing Gitea provider; don't create a separate provider
- **Ref pattern detection**: Parse `refs/for/*` patterns in webhook payloads
- **Backward compatibility**: Ensure non-agit Gitea workflows continue to work
- **Configuration flag**: Add optional `agit_enabled` flag to Gitea VCS config
- **Reuse existing PR APIs**: Once an agit PR is created, it behaves like a normal PR

## 6. Risks and Unknowns

### Technical Risks
1. **Webhook payload differences**: Agit push events may have different webhook structure than standard PR events
   - *Mitigation*: Capture and document real agit webhooks early; handle both formats
   
2. **PR number resolution**: Agit push doesn't immediately return a PR number
   - *Mitigation*: Use Gitea API to query PR by head ref after push event
   
3. **Race conditions**: Webhook may arrive before PR is fully created in Gitea
   - *Mitigation*: Add retry logic with exponential backoff for PR lookups

4. **Gitea version fragmentation**: Agit support and API behavior may vary by version
   - *Mitigation*: Test against multiple Gitea versions (1.13+, 1.17+, 1.21+)

5. **Forgejo compatibility**: Forgejo is a Gitea fork; agit behavior may diverge
   - *Mitigation*: Test on both Gitea and Forgejo; document any differences

### Process Risks
1. **Upstream acceptance**: Atlantis maintainers may reject or heavily revise the approach
   - *Mitigation*: Open a discussion issue before coding to align on approach

2. **Maintenance burden**: Agit is less common than GitHub/GitLab workflows
   - *Mitigation*: Provide comprehensive tests and docs to reduce support load

3. **Breaking changes**: Implementation may require refactoring Gitea client
   - *Mitigation*: Use feature flags and maintain backward compatibility

### Unknowns
- Does Gitea send webhooks for agit pushes, or only for resulting PRs?
- Are agit options (draft, reviewers) exposed in webhook payload or require API call?
- How does Gitea handle failed agit pushes (e.g., target branch doesn't exist)?
- Will Atlantis's existing Gitea client need OAuth scope changes for agit?

### Blockers
- **No Gitea instance access**: Need a test Gitea instance (can use Docker)
- **Atlantis codebase familiarity**: Requires reading and understanding existing VCS abstractions
- **Go development environment**: Need Go 1.21+ and Atlantis dev dependencies

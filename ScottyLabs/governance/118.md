# Implementation Plan: Organization-Wide Issue Labels for terraform-provider-forgejo

## 1. Problem Analysis

### What needs to be solved
Create a Terraform resource to manage **organization-wide issue labels** in Forgejo/Gitea. Currently, labels must be managed per-repository, but Forgejo supports organization-level labels that can be preset and reused across all repositories within an organization.

### Why this matters
- **Consistency**: Organization-wide labels ensure consistent labeling conventions across all repositories
- **Efficiency**: Define labels once at the org level instead of recreating them in every repository
- **Maintenance**: Update label definitions centrally without touching individual repos
- **Onboarding**: New repositories automatically inherit the organization's label schema

### Current state
- The terraform-provider-forgejo likely has repository-level label resources
- No resource exists for managing organization-level labels
- Forgejo/Gitea API supports org-level label endpoints (to be verified)

---

## 2. Technical Approach

### Strategy
1. **Research Gitea/Forgejo API**: Identify the exact API endpoints for org-level labels
2. **Create new Terraform resource**: `forgejo_org_label` (or similar naming)
3. **Implement CRUD operations**: Create, Read, Update, Delete for org labels via API
4. **Schema definition**: Define Terraform resource schema matching Gitea API label model
5. **Testing**: Unit tests and acceptance tests for the new resource

### Key Decisions

**Decision 1: Resource naming**
- **Choice**: `forgejo_org_label` (singular) 
- **Rationale**: Follows Terraform convention of singular resource names; mirrors likely existing `forgejo_repository_label` pattern

**Decision 2: API endpoint discovery**
- **Research needed**: Verify Gitea/Forgejo API version and exact endpoints
- **Expected pattern**: `GET/POST/PATCH/DELETE /orgs/{org}/labels`

**Decision 3: Label schema attributes**
- **Minimum fields**: `name`, `color`, `description`, `organization`
- **Color format**: Hex code without `#` prefix (standard in Gitea)
- **ID handling**: Gitea uses numeric IDs for labels

**Decision 4: Import support**
- **Include**: Terraform import functionality using format `org/label_id` or `org/label_name`
- **Rationale**: Enable managing existing org labels via Terraform

## 3. Implementation Steps

### Phase 1: Research & Design (1-2 hours)
1. Clone the terraform-provider-forgejo repository
2. Review existing repository label resource implementation for patterns
3. Test Gitea/Forgejo API endpoints for org labels:
   ```bash
   # Test endpoints (example)
   curl -H "Authorization: token XXX" https://gitea.example.com/api/v1/orgs/{org}/labels
   ```
4. Document API request/response structures
5. Identify provider SDK patterns used (likely terraform-plugin-sdk or terraform-plugin-framework)

### Phase 2: Resource Implementation (3-4 hours)
1. Create new resource file: `internal/provider/resource_org_label.go` (adjust path based on project structure)
2. Define resource schema:
   - `organization` (string, required, ForceNew)
   - `name` (string, required)
   - `color` (string, required) - 6-char hex without `#`
   - `description` (string, optional)
3. Implement `Create` function:
   - Validate color format (regex: `^[0-9a-fA-F]{6}$`)
   - POST to `/api/v1/orgs/{org}/labels`
   - Set resource ID
4. Implement `Read` function:
   - GET from `/api/v1/orgs/{org}/labels/{id}` or list and filter
   - Handle 404 (label deleted outside Terraform)
5. Implement `Update` function:
   - PATCH to `/api/v1/orgs/{org}/labels/{id}`
   - Allow updating name, color, description
6. Implement `Delete` function:
   - DELETE to `/api/v1/orgs/{org}/labels/{id}`
7. Implement `ImportState` function:
   - Parse import ID format `org/label_id`
   - Populate state from API

## 6. Risks & Unknowns

### Blockers
1. **API endpoint availability**: 
   - **Risk**: Forgejo/Gitea version may not support org-level labels
   - **Mitigation**: Check API documentation for minimum version; document version requirements

2. **Upstream provider structure**:
   - **Risk**: Provider may use different file/package structure than assumed
   - **Mitigation**: Study existing provider code first (Phase 1)

3. **Authentication/permissions**:
   - **Risk**: Org label management may require org owner permissions
   - **Mitigation**: Document required permission level; test with appropriate credentials

### Unknowns
1. **API endpoint exact path**: May differ from repository labels
2. **Label ID format**: May be string vs integer
3. **Concurrent modification handling**: How Gitea handles race conditions
4. **Provider SDK version**: May use plugin-framework vs plugin-sdk
5. **Existing tests setup**: May need Forgejo test instance configuration

### Technical Debt
- **No batch operations**: Creating multiple labels requires multiple resources (acceptable for MVP)
- **No label templates**: Cannot define label sets for auto-application (future enhancement)
- **No conflict resolution**: If label exists with same name, update vs error behavior needs definition

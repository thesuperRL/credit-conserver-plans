# Implementation Plan: Support Multiple Sentry Projects per `Repo`

## 1. Problem Analysis

### What needs to be solved
This project currently has **no error tracking or monitoring system**. The issue requests adding Sentry integration with support for **multiple Sentry projects** per repository configuration.

**Current state:**
- No Sentry SDK integration
- Simple `RepoConfig` with only `platform` and `name` fields
- Error handling exists but errors only go to logs, not a monitoring system
- The feature is blocked waiting on https://github.com/cachix/secretspec/pull/163 (likely a dependency that provides secret management for Sentry DSNs)

**Why this matters:**
- **Production visibility**: Track errors across multiple monitored repositories in real-time
- **Multi-environment support**: A single repo may need different Sentry projects for dev/staging/prod
- **Per-component tracking**: Large repos may want separate Sentry projects for frontend/backend/workers
- **Correlation**: Link GitHub issues to Sentry error reports for better triage

### Assumptions
- The secretspec PR will provide a mechanism to securely store/retrieve Sentry DSNs (Data Source Names)
- "Multiple Sentry projects per Repo" means one `RepoConfig` can send errors to 1+ Sentry projects
- Sentry integration should be **optional** (repos without Sentry config continue working unchanged)
- Errors should be captured during issue processing, plan generation, and PR operations

---

## 2. Technical Approach

### Strategy
**Lazy integration approach** (ponytail mode):
1. Use official `sentry-sdk` package (stdlib for error tracking)
2. Add **optional** `sentry_projects` list to `RepoConfig` dataclass
3. Initialize Sentry SDK once per repo processing cycle with multiple DSNs via Sentry's environment/tag filtering
4. **No custom error handling**: Sentry SDK auto-captures exceptions via its integration hooks
5. Defer secretspec integration until PR #163 is merged (use environment variables initially)

### Key decisions

| Decision | Rationale |
|----------|-----------|
| **List of Sentry DSNs** | Simple, explicit. Each DSN = one Sentry project. |
| **Optional field** | Backward compatible. Repos without Sentry continue working. |
| **SDK auto-capture** | Sentry SDK automatically captures exceptions in `try/except` blocks without code changes. |
| **Tags for repo context** | Each error tagged with `repo_name`, `platform`, `issue_number` for filtering in Sentry UI. |
| **Environment variables first** | Start with `SENTRY_DSN_<OWNER_REPO>` pattern, migrate to secretspec later. |
| **Single DSN at a time** | Sentry SDK doesn't natively support multiple DSNs simultaneously. Workaround: initialize per-project or use Sentry Hub per DSN. |

### Alternative considered: Sentry Hub per project
Sentry supports `Hub` abstraction for multiple isolated clients. We could create a Hub per Sentry project and send errors to all of them. **Rejected**: Over-engineered for v1. Start with first DSN in list, add multi-DSN in follow-up if needed.

**Chosen approach:** Accept list of DSNs in config, but only initialize SDK with the **first DSN** initially. Document this limitation. Add multi-DSN support later if requested.

## 6. Risks & Unknowns

### Blockers
- **secretspec PR #163**: This issue explicitly states it's waiting on https://github.com/cachix/secretspec/pull/163
  - **Mitigation**: Implement basic Sentry support with env vars first. Add secretspec integration as Phase 2 after PR merges.
  - **Timeline unknown**: Cannot complete full implementation until dependency is ready.

### Technical risks
- **Multiple DSNs not fully supported**: Sentry SDK's `init()` accepts one DSN. Supporting true multi-project requires using `Hub` API or multiple SDK instances.
  - **Mitigation**: Document "only first DSN used" limitation. Add TODO for multi-DSN support.
  - **Upgrade path**: Use `sentry_sdk.Hub()` to create isolated clients per DSN if needed later.

- **Config format change**: Switching from `"codeberg:ScottyLabs/infrastructure"` string to structured dict breaks existing configs.
  - **Mitigation**: Keep backward compatibility. Accept both formats:
    ```yaml
    # Old format (still works)
    - "codeberg:ScottyLabs/infrastructure"
    
    # New format (for Sentry)
    - platform: codeberg
      name: ScottyLabs/infrastructure
      sentry_dsns: ["https://..."]
    ```
  - **Implementation**: Update `RepoConfig.parse()` to accept dict or string.

- **Environment variable naming**: `SENTRY_DSN_SCOTTYLABS_INFRASTRUCTURE` becomes unwieldy for long repo names.
  - **Mitigation**: Use simple `SENTRY_DSN` for single-repo setups. Per-repo env vars are optional override.

### Unknowns
- **What does secretspec provide?**: Without seeing PR #163, unclear if it changes config schema, adds new modules, or just provides secret retrieval API.
  - **Mitigation**: Implement environment-variable-based Sentry first. Refactor to secretspec once available.

- **Sentry performance impact**: SDK adds overhead to every exception (even caught ones).
  - **Mitigation**: Sentry SDK is lazy. Disable in local dev by not providing DSN. Production only.

- **Sentry quota limits**: Free tier has event limits. Could hit quota if errors spike.
  - **Mitigation**: Configure sample rate if needed: `sentry_sdk.init(dsn=..., sample_rate=0.5)`. Start at 100%.

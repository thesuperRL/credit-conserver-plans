# Implementation Plan: External Database Backup System

## 1. Problem Analysis

### Current State
The credit-conserver application is currently a **stateless GitHub Actions workflow** that:
- Processes issues ephemerally without persistent storage
- Stores all state in Git (PRs, commits, markdown files)
- Tracks processed issues via GitHub labels
- Runs in ephemeral containers on GitHub Actions runners

### Problem Statement
Issue #95 requests external backup capabilities for database services. This indicates one of two scenarios:

1. **Future Architecture**: Plan to add persistent storage (likely for credit tracking, issue caching, or analytics)
2. **Misunderstanding**: The issue may incorrectly assume databases exist

### Why This Needs to Be Solved
If databases are added in the future, external backups are critical for:
- **Data durability**: Protection against accidental deletion, corruption, or infrastructure failures
- **Compliance**: Meeting data retention and recovery requirements
- **Disaster recovery**: Ability to restore service after catastrophic events
- **Point-in-time recovery**: Rollback to specific timestamps during incidents
- **Geographic redundancy**: Protection against regional cloud provider outages

## 2. Technical Approach

### Strategy
Implement a **layered backup system** using cloud-native services with the following principles:
- **Automated**: Scheduled backups with no manual intervention
- **Encrypted**: At-rest and in-transit encryption
- **Versioned**: Retain multiple backup generations
- **Tested**: Regular restore validation
- **Monitored**: Alerting on backup failures

### Assumptions
Since no databases currently exist, this plan assumes:
- **Future database**: PostgreSQL (most common choice for this type of application)
- **Deployment target**: Continue using GitHub Actions, with database hosted on a cloud provider
- **Cloud provider**: AWS (can be adapted to GCP/Azure)
- **Backup destination**: AWS S3 with cross-region replication

### Key Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Database | PostgreSQL | Best support for structured data, ACID compliance, mature backup ecosystem |
| Backup tool | pg_dump + custom scripts | Native PostgreSQL tool, reliable, no external dependencies |
| Storage | AWS S3 | Durable (11 9s), cheap, versioning built-in |
| Encryption | AWS KMS | Managed key rotation, audit trail, FIPS compliance |
| Scheduling | GitHub Actions cron | Leverage existing infrastructure |
| Retention | 7 daily, 4 weekly, 12 monthly | Balance cost vs. recovery granularity |

## 3. Implementation Steps

### Phase 1: Infrastructure Setup (Estimated: 2-4 hours)

1. **Create AWS resources** (if using AWS):
   ```bash
   # S3 bucket for backups
   - Primary bucket: credit-conserver-backups-primary (us-east-1)
   - Replica bucket: credit-conserver-backups-replica (us-west-2)
   - Enable versioning, encryption (AES-256), lifecycle policies
   
   # IAM credentials
   - Create backup-specific IAM user with minimal permissions
   - Generate access keys for GitHub Actions secrets
   ```

2. **Configure GitHub Secrets**:
   - `AWS_BACKUP_ACCESS_KEY_ID`
   - `AWS_BACKUP_SECRET_ACCESS_KEY`
   - `DB_BACKUP_ENCRYPTION_KEY`
   - `DATABASE_URL` (PostgreSQL connection string)
   - `BACKUP_NOTIFICATION_EMAIL` (for failure alerts)

3. **Set up S3 bucket policies**:
   - Lifecycle rules: transition to Glacier after 30 days, expire after 365 days
   - Cross-region replication to secondary bucket
   - Block public access

### Phase 2: Backup Scripts (Estimated: 3-4 hours)

4. **Create backup script** (`scripts/backup_database.sh`):
   - Generate timestamped backup using `pg_dump`
   - Compress with `gzip`
   - Encrypt with GPG
   - Upload to S3 with metadata tags
   - Validate upload integrity
   - Clean up local files
   - Send notification on failure

5. **Create restore script** (`scripts/restore_database.sh`):
   - List available backups from S3
   - Download specified backup
   - Decrypt and decompress
   - Validate schema compatibility
   - Restore with `pg_restore` or `psql`
   - Run post-restore validation queries

6. **Create backup verification script** (`scripts/verify_backup.sh`):
   - Download latest backup
   - Spin up temporary PostgreSQL container
   - Restore backup to temp database
   - Run schema validation queries
   - Compare row counts with production
   - Report validation results

### Phase 3: GitHub Actions Integration (Estimated: 2-3 hours)

7. **Create backup workflow** (`.github/workflows/database_backup.yml`):
   - Scheduled cron: daily at 2 AM UTC
   - Manual trigger for ad-hoc backups
   - Matrix strategy for multiple databases (if needed)
   - Artifact retention for workflow logs

8. **Create verification workflow** (`.github/workflows/verify_backups.yml`):
   - Weekly schedule to test restore process
   - Uses separate test database
   - Reports to monitoring system

9. **Add monitoring and alerting**:
   - Use GitHub Actions status checks
   - Email notifications on failure
   - Optional: integrate with Slack/PagerDuty

### Phase 4: Documentation & Testing (Estimated: 2-3 hours)

10. **Write runbook documentation** (`docs/BACKUP_RECOVERY.md`):
    - How to trigger manual backup
    - How to restore from backup (step-by-step)
    - How to verify backup integrity
    - Troubleshooting common issues
    - Disaster recovery procedures

11. **Add configuration file** (`config/backup_config.yml`):
    - Retention policies
    - Backup windows
    - Notification settings
    - S3 bucket names
    - Database connection settings

12. **Test all procedures**:
    - Run manual backup
    - Verify backup uploaded to S3
    - Test restore to staging database
    - Validate automated schedule triggers
    - Test failure notifications

## 5. Testing Strategy

### Unit Tests
- **Script validation**: Test each backup script with mock data
  - `tests/test_backup_script.sh`: Verify backup creation, compression, encryption
  - `tests/test_restore_script.sh`: Verify decryption, decompression, restore process
  - Use PostgreSQL Docker container for isolated testing

### Integration Tests
- **End-to-end backup workflow**:
  1. Create test database with known data
  2. Run backup script
  3. Verify S3 upload
  4. Destroy test database
  5. Restore from backup
  6. Verify data integrity (checksums, row counts)

### Validation Criteria
- ✅ Backup completes within 10 minutes (for databases < 10GB)
- ✅ Encrypted backup uploaded to S3 with correct metadata
- ✅ Restore completes successfully with 100% data fidelity
- ✅ Automated schedule triggers as expected
- ✅ Failure notifications sent within 5 minutes of error
- ✅ Cross-region replication completes within 1 hour
- ✅ Lifecycle policies correctly archive old backups

### Manual Testing Checklist
```
□ Manual backup trigger works
□ Scheduled backup runs at correct time
□ Backup appears in S3 with timestamp
□ Backup is encrypted (attempt raw read fails)
□ Restore script lists available backups
□ Restore to staging database succeeds
□ Restored data matches production
□ Old backups transition to Glacier
□ Failure triggers email notification
□ Cross-region replica exists
```

## 6. Risks & Blockers

### High-Priority Risks

| Risk | Impact | Likelihood | Mitigation |
|------|--------|------------|------------|
| **No database exists** | Plan is currently not applicable | HIGH | Verify with stakeholders if database is planned; if not, close issue |
| **Backup window exceeds GitHub Actions limit** | Backups fail on large databases (6hr timeout) | MEDIUM | Use incremental backups; consider AWS RDS automated backups instead |
| **Encryption key loss** | Cannot decrypt backups (data loss) | LOW | Store key in multiple secure locations; document key rotation |
| **S3 costs spiral** | Large databases = expensive storage | MEDIUM | Implement aggressive lifecycle policies; monitor costs |
| **Restore never tested** | Discover backups corrupt during disaster | MEDIUM | Automated weekly restore validation |
| **Secrets exposure** | Database credentials leaked in logs | MEDIUM | Use secret masking, audit workflow logs |

### Technical Blockers

1. **Database doesn't exist yet**: This entire plan is blocked until persistent storage is added
2. **Cloud provider account**: Need AWS (or equivalent) account with billing enabled
3. **Database access**: Backup user needs `pg_dump` privileges
4. **Network egress costs**: Transferring large backups from database host to S3 may incur costs
5. **GitHub Actions runner resources**: Limited disk space (14GB) for temporary backup files

### Open Questions

- **Which database will be used?** (PostgreSQL assumed, but could be MySQL, MongoDB, etc.)
- **Where is the database hosted?** (AWS RDS, self-hosted, Heroku, etc.)
- **What is the database size?** (Affects backup strategy and costs)
- **Is this database planned or does it already exist elsewhere?** (Critical clarification needed)
- **What are the compliance requirements?** (GDPR, HIPAA, etc. may dictate retention periods)
- **Who needs restore access?** (IAM permissions, emergency contact list)

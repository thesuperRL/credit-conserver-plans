# Implementation Plan: Discord Observability Notifications with Embeds

## 1. Problem Analysis

### Current State
The credit-conserver workflow runs automatically via GitHub Actions (every 6 hours) and processes multiple repositories in parallel. Currently, there is no Discord notification system in place. Users have no real-time visibility into:
- Workflow start/completion status
- Issues being processed
- PRs being created
- Change requests being handled
- Credit budget consumption
- Errors or failures

### Proposed Solution
Implement Discord webhook notifications using rich embeds to provide structured, color-coded observability into the workflow's execution. The notifications should be:
- **Visually appealing**: Use Discord embeds with appropriate colors, fields, and formatting
- **Informative**: Show key metrics without overwhelming detail
- **Actionable**: Include links to PRs, issues, and workflow runs
- **Parseable**: Use structured fields instead of plain text dumps

### Why Embeds?
Discord embeds provide:
- Color-coded status indicators (green=success, yellow=warning, red=error)
- Structured field layout (inline fields for metrics)
- Embedded links and formatting
- Thumbnail/image support
- Footer metadata (timestamp, workflow info)

## 2. Technical Approach

### Strategy
1. **Add Discord webhook configuration** to `config.yml` and environment variables
2. **Create a Discord notifier module** (`modules/discord_notifier.py`) that wraps webhook POST requests with embed formatting
3. **Integrate notification calls** at key workflow points (start, repo completion, final summary, errors)
4. **Use structured embeds** with appropriate colors and field layouts
5. **Make notifications optional** - gracefully degrade if webhook URL not configured

### Key Design Decisions

#### Notification Points
- **Workflow Start**: Single embed with configuration summary
- **Repo Completed**: Per-repo embed with processed issues, PRs created, change requests handled
- **Workflow Complete**: Summary embed with aggregate statistics across all repos
- **Error Events**: Error embed with failure details

#### Embed Design
- **Color Coding**:
  - Green (0x28a745): Success/completion
  - Blue (0x0366d6): Information/start
  - Orange (0xfb8c00): Warnings/partial success
  - Red (0xcb2431): Errors/failures
  
- **Field Structure**:
  - Use inline fields for metrics (3 per row)
  - Use non-inline fields for detailed content (logs, links)
  - Include timestamp in footer
  - Add workflow run URL in description

#### Error Handling
- Wrap all Discord POST calls in try/except
- Log Discord notification failures but don't block workflow
- Add timeout (5 seconds) to prevent hanging
- Return boolean success/failure for observability

## 6. Risks and Unknowns

### Technical Risks
1. **Discord rate limits**: Discord webhooks have rate limits (~30 requests per 60 seconds per webhook)
   - **Mitigation**: Batch notifications, add rate limit backoff
   - **Impact**: Low - workflows process 5-10 repos, won't hit limits under normal use

2. **Webhook availability**: Network issues or Discord outages could cause notification failures
   - **Mitigation**: Wrap all webhook calls in try/except, log failures, continue workflow
   - **Impact**: Low - notifications are observability, not critical path

3. **Embed size limits**: Discord embeds have character limits (title 256, description 4096, fields 1024)
   - **Mitigation**: Truncate long content with "..." suffix, add "See logs for full details"
   - **Impact**: Medium - large error messages or repo lists may need truncation

4. **Configuration complexity**: Adding another config option increases setup burden
   - **Mitigation**: Make Discord webhook optional, provide clear setup docs
   - **Impact**: Low - optional feature, skip if not needed

### Unknown Variables
1. **Optimal notification frequency**: Should we notify per-issue or batch by repo?
   - **Decision**: Batch by repo (lower noise, better aggregation)
   
2. **Error notification threshold**: Should we notify on every error or aggregate?
   - **Decision**: Aggregate errors into summary embed, send dedicated error embed only for critical failures

3. **Notification content preferences**: What fields/metrics are most valuable?
   - **Decision**: Start with core metrics (issues processed, PRs created, tokens used), iterate based on feedback

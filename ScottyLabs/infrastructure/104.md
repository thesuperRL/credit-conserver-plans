# Implementation Plan: Grafana Dashboard for LLM Usage Statistics

## 1. Problem Analysis

### Current State
- The system uses Claude API via local `claude` CLI for generating implementation plans and commit messages
- Token usage is tracked in-memory via `CreditTracker` but not persisted or visualized
- The issue mentions "litellm dashboard" being limited to 5 users (free tier), suggesting either:
  - The team plans to use LiteLLM proxy in the future
  - There's confusion about what monitoring tool is being used
  - A separate LiteLLM deployment exists that this system should integrate with

### Problem
Need a self-hosted Grafana dashboard that:
- Tracks LLM usage statistics (tokens, costs, requests, models)
- Supports unlimited users (no SaaS tier limits)
- Works independently of LiteLLM dashboard restrictions
- Provides visibility into credit consumption patterns

### Why This Matters
- Current in-memory tracking disappears after each run
- No historical data for budget planning
- No visibility into per-repo, per-model, or per-operation costs
- Cannot identify usage patterns or optimization opportunities

## 2. Technical Approach

### Strategy
**Metrics Collection → Time-Series Storage → Visualization**

1. **Metrics Exporter**: Add Prometheus-compatible metrics endpoint or push to Prometheus Pushgateway
2. **Time-Series Database**: Use Prometheus to store metrics
3. **Visualization**: Grafana dashboard consuming Prometheus data

### Key Decisions

**Decision 1: Push vs Pull Metrics**
- **Choice**: Push to Prometheus Pushgateway
- **Rationale**: GitHub Actions runs are ephemeral; no long-running process for Prometheus to scrape
- **Trade-off**: Slightly more complex setup vs. standard pull model

**Decision 2: Metrics Format**
- **Choice**: Prometheus format (OpenMetrics standard)
- **Rationale**: Native Grafana support, industry standard, rich aggregation functions
- **Alternative considered**: InfluxDB (more complex, unnecessary for this use case)

**Decision 3: Integration Point**
- **Choice**: Extend `CreditTracker` to emit metrics after each API call
- **Rationale**: Single source of truth, minimal code changes, already tracks all usage
- **Trade-off**: Coupled to credit tracking vs. separate metrics module

**Decision 4: Metrics Granularity**
Track at three levels:
- **Per-request**: model, operation type, tokens, latency
- **Per-repo**: aggregated by repository
- **Per-run**: workflow execution metadata

## 3. Implementation Steps

### Phase 1: Metrics Collection (Core)
1. Add `prometheus_client` to `requirements.txt`
2. Create `modules/metrics_exporter.py`:
   - `MetricsExporter` class wrapping Prometheus CollectorRegistry
   - Counter for total requests
   - Histogram for token usage (input/output separate)
   - Gauge for current budget usage percentage
   - Labels: `model`, `operation` (plan/commit/pr_summary), `repo`, `platform`
3. Extend `CreditTracker.record_usage()` to accept metrics exporter and emit metrics
4. Update `AnthropicClient` methods to pass operation type to credit tracker

### Phase 2: Metrics Push (GitHub Actions Integration)
1. Add Pushgateway URL to `config.yml` and environment variables
2. Create `modules/metrics_pusher.py`:
   - `push_to_gateway()` function using `prometheus_client.push_to_gateway`
   - Error handling for network failures (graceful degradation)
3. Update `ParallelWorkflowRunner.run()`:
   - Initialize `MetricsExporter` at start
   - Pass to all workers
   - Push metrics after workflow completion (finally block)
4. Add workflow summary metrics (total time, repos processed, issues handled)

### Phase 3: Infrastructure Setup
1. Create `docker-compose.yml` for local testing:
   - Prometheus container

3. Create `grafana/provisioning/dashboards/dashboard.yml` (dashboard provider config)
4. Create `prometheus.yml` with Pushgateway scrape config

### Phase 4: Dashboard Design
Create `grafana/dashboards/litellm_usage.json`:

**Panel 1**: Total Tokens Used (Time Series)
- Query: `sum(llm_tokens_total{type="input"}) by (model) + sum(llm_tokens_total{type="output"}) by (model)`
- Visualization: Line graph
- Legend: By model

**Panel 2**: Token Distribution (Pie Chart)
- Query: `sum(llm_tokens_total) by (operation)`
- Shows breakdown: plan generation vs commit generation vs PR summaries

**Panel 3**: Cost Estimate (Gauge)
- Query: `(sum(llm_tokens_total{model=~".*sonnet.*",type="input"}) * 0.000003) + (sum(llm_tokens_total{model=~".*sonnet.*",type="output"}) * 0.000015) + (sum(llm_tokens_total{model=~".*haiku.*",type="input"}) * 0.00000025) + (sum(llm_tokens_total{model=~".*haiku.*",type="output"}) * 0.00000125)`
- Based on current Anthropic pricing

**Panel 4**: Request Rate (Time Series)
- Query: `rate(llm_requests_total[5m])`
- Shows requests per second

**Panel 5**: Budget Utilization (Gauge)
- Query: `llm_budget_usage_percent`
- Shows current run's percentage

**Panel 6**: Per-Repo Token Usage (Bar Chart)
- Query: `sum(llm_tokens_total) by (repo)`
- Identifies high-usage repositories

**Panel 7**: Average Tokens per Request (Stat)
- Query: `sum(llm_tokens_total) / sum(llm_requests_total)`

**Panel 8**: Request Latency (Histogram)
- Query: `histogram_quantile(0.95, rate(llm_request_duration_seconds_bucket[5m]))`
- Shows p95 latency

## 6. Risks & Mitigations

### Risk 1: Pushgateway is Single Point of Failure
**Impact**: If Pushgateway is down, metrics push fails
**Mitigation**: 
- Wrap push in try/except, log warning but don't fail workflow
- Consider Grafana Cloud alternative (managed, HA)
- Document fallback to checking GitHub Actions logs

### Risk 2: Prometheus Data Retention
**Impact**: Default retention is 15 days; historical data lost
**Mitigation**:
- Configure Prometheus `--storage.tsdb.retention.time=90d` in docker-compose
- Document backup strategy for Prometheus data volume
- Consider long-term storage solution (Thanos, Cortex) if needed later

### Risk 3: Metric Label Cardinality Explosion
**Impact**: Too many unique label combinations → Prometheus performance issues
**Mitigation**:
- Limit labels to: model (5 values), operation (3 values), platform (2 values), repo (N repos)
- Avoid including issue numbers or commit SHAs as labels
- Document label schema in code comments

### Risk 4: Pushgateway Accumulation
**Impact**: Pushgateway accumulates metrics from all runs; old data not cleared
**Mitigation**:
- Use `replace` grouping strategy, not `add`
- Include `run_id` in job label to separate runs
- Document manual cleanup: `curl -X DELETE http://pushgateway:9091/metrics/job/triage_bot`

### Risk 5: Grafana Dashboard Drift
**Impact**: Manual edits to dashboard not captured in repo
**Mitigation**:
- Use provisioning (JSON in repo) for dashboard definition
- Document export process: "Export JSON" → save to `grafana/dashboards/`
- Add pre-commit hook to validate JSON syntax (optional)

### Risk 6: Cost Calculation Accuracy
**Impact**: Anthropic pricing changes → cost panel shows wrong values
**Mitigation**:
- Add comment in dashboard JSON with pricing source and last update date
- Create alert if cost seems anomalous (sudden 10x increase)
- Document quarterly pricing review in MONITORING.md

### Unknown: LiteLLM Integration
**Impact**: Issue mentions LiteLLM but codebase uses Claude directly
**Clarification needed**:
- Is there a separate LiteLLM proxy deployment?
- Should this system send requests through LiteLLM proxy instead of direct Claude API?
- If yes, LiteLLM has built-in Prometheus metrics; use those instead of custom metrics

**Mitigation**:
- Design metrics schema compatible with LiteLLM format
- If switching to LiteLLM later, only `anthropic_client.py` needs changes
- Dashboard can query either source with minor PromQL adjustments

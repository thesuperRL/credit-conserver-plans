# Implementation Plan: Manage Runner Registration Token with Terranix

## 1. Problem Analysis

### What Needs to Be Solved
- **Current State**: The credit-conserver workflow uses GitHub-hosted runners (`ubuntu-latest`), which have limited compute resources and incur GitHub Actions minutes usage
- **Target State**: Implement self-hosted GitHub Actions runners with registration token management via terranix (Terraform + Nix)
- **Core Challenge**: GitHub runner registration tokens expire after 1 hour and must be rotated regularly. Manual token management is error-prone and doesn't scale

### Why This Matters
- **Cost Efficiency**: Self-hosted runners eliminate GitHub Actions minutes costs for intensive workloads
- **Control**: Custom compute resources, persistent caching, and environment configuration
- **Automation**: Terranix enables declarative infrastructure-as-code with Nix's reproducibility guarantees
- **Security**: Automated token rotation reduces the risk of expired or leaked credentials

## 2. Technical Approach

### Strategy
1. **Infrastructure Layer**: Use terranix to define GitHub runner infrastructure declaratively
2. **Token Management**: Leverage GitHub API to fetch registration tokens programmatically
3. **Secret Management**: Store tokens securely using environment variables or secret management solutions
4. **Runner Lifecycle**: Automate runner registration, health checks, and de-registration
5. **Nix Integration**: Package runner dependencies and configuration as reproducible Nix derivations

### Key Decisions
- **Terranix over raw Terraform**: Better integration with Nix ecosystem, type-safe configuration
- **GitHub API for tokens**: Use `POST /repos/{owner}/{repo}/actions/runners/registration-token` endpoint
- **Token refresh strategy**: Fetch new token on each runner startup (tokens valid for 1 hour)
- **Storage**: Avoid storing tokens in version control; fetch dynamically or use external secrets manager
- **Scope**: Repository-level runners (not organization-level) to match current `TARGET_REPOS` pattern

## 3. Implementation Steps

### Phase 1: Infrastructure Setup
1. **Create terranix directory structure**
   - `terraform/` - Root directory for infrastructure code
   - `terraform/main.nix` - Main terranix configuration
   - `terraform/runner.nix` - GitHub Actions runner module
   - `terraform/secrets.nix` - Secret management configuration

2. **Define GitHub provider configuration**
   - Configure GitHub provider in terranix
   - Set up authentication using `GITHUB_TOKEN`

3. **Create runner registration module**
   - Define null_resource or local-exec provisioner to fetch registration tokens
   - Use GitHub API to get fresh tokens on apply
   - Configure runner with token

### Phase 2: Token Management
4. **Implement token fetching logic**
   - Create shell script or Python module to call GitHub API
   - Endpoint: `POST https://api.github.com/repos/{owner}/{repo}/actions/runners/registration-token`
   - Parse response to extract `token` field (valid for 1 hour)

5. **Integrate token refresh into runner lifecycle**
   - Fetch token dynamically during runner startup
   - No persistent storage of tokens
   - Handle token expiration gracefully with retry logic

6. **Add error handling**
   - API rate limiting
   - Network failures
   - Invalid credentials

### Phase 3: Runner Configuration
7. **Package runner dependencies in Nix**
   - GitHub Actions runner binary
   - Python 3.11+ for credit-conserver
   - Required pip dependencies from `requirements.txt`
   - Git and other build tools

8. **Create NixOS module or shell.nix**
   - Reproducible runner environment
   - Auto-start on boot
   - Health check monitoring

9. **Configure runner labels and tags**
   - Label: `credit-conserver`
   - Match in workflow: `runs-on: [self-hosted, credit-conserver]`

### Phase 4: Integration
10. **Update GitHub Actions workflow**
    - Modify `.github/workflows/triage.yml`
    - Change `runs-on: ubuntu-latest` to `runs-on: [self-hosted, credit-conserver]`
    - Add fallback to hosted runners if self-hosted unavailable

11. **Add deployment documentation**

12. **Create Makefile or flake.nix**
    - `make apply` - Deploy infrastructure

## 6. Risks

### Critical Blockers
- **GitHub API rate limits**: Token endpoint has rate limits; need to implement backoff/retry
  - *Mitigation*: Cache tokens in memory for their 1-hour validity, fetch only when expired
  
- **Token expiration during long runs**: If workflow runs >1 hour, token may expire mid-execution
  - *Mitigation*: Tokens only needed for initial registration; running workflows are unaffected

- **Network reliability**: Self-hosted runners need stable connectivity to github.com
  - *Mitigation*: Implement health checks and auto-restart on connection loss

### Medium Risks
- **Nix/terranix learning curve**: Team unfamiliarity with ecosystem
  - *Mitigation*: Provide comprehensive documentation and examples

- **Infrastructure costs**: Self-hosted runners require compute resources
  - *Mitigation*: Document cost comparison; use spot/preemptible instances

- **Secret management complexity**: GITHUB_TOKEN must have `repo` and `admin:org` scopes
  - *Mitigation*: Document required permissions clearly; use fine-grained PATs

### Unknowns
- **Optimal runner count**: How many parallel runners needed for `max_parallel_repos: 5`?
  - *Investigation*: Start with 2 runners, scale based on queue depth metrics

- **Storage requirements**: Do plan markdown files and logs accumulate?
  - *Investigation*: Monitor disk usage; implement log rotation if needed

# Implementation Plan: Change Forgejo Sending Email to noreply@cmu.dev

## 1. Problem Analysis

### What needs to be solved
Forgejo (a Gitea fork) is currently configured to send emails from a different address, and needs to be changed to use `noreply@cmu.dev` as the sender address for all outgoing emails (notifications, password resets, etc.).

### Why this matters
- **Brand consistency**: Using the `cmu.dev` domain maintains organizational branding
- **Email deliverability**: A dedicated noreply address reduces risk of legitimate emails being flagged as spam
- **User clarity**: Recipients immediately recognize the source as automated CMU infrastructure
- **Security best practices**: Separating automated emails from user mailboxes prevents reply confusion

### Current state assumptions
- Forgejo instance is deployed (likely on ScottyLabs infrastructure)
- Email functionality is already configured and working
- Configuration is managed via `app.ini` file or environment variables
- Access to the deployment environment is available

## 2. Technical Approach

### Strategy
Modify Forgejo's mailer configuration to set the `FROM` email address to `noreply@cmu.dev`. Forgejo uses a single configuration file (`app.ini`) or environment variables for all settings.

### Key decisions
1. **Configuration method**: Use `app.ini` modification (most common for self-hosted Forgejo)
2. **Scope**: Change only the sender address, preserve existing SMTP settings
3. **Validation**: Test email sending after change to confirm delivery
4. **Rollback plan**: Keep backup of original configuration

### Forgejo email configuration structure
Forgejo's `[mailer]` section controls email settings:
```ini
[mailer]
ENABLED = true
FROM = noreply@cmu.dev           # ← This is what we're changing
MAILER_TYPE = smtp
HOST = smtp.example.com:587
IS_TLS_ENABLED = true
USER = smtp_username
PASSWD = smtp_password
```

## 3. Implementation Steps

1. **Locate the Forgejo configuration file**
   - SSH into the Forgejo server
   - Find `app.ini` (common paths: `/etc/forgejo/app.ini`, `/var/lib/forgejo/custom/conf/app.ini`, or docker volume mount)
   - Alternatively, check for environment variable configuration

2. **Backup current configuration**
   - `cp app.ini app.ini.backup.$(date +%Y%m%d)`
   - Document current `FROM` value for rollback

3. **Modify the mailer FROM setting**
   - Edit the `[mailer]` section
   - Change `FROM = <current-address>` to `FROM = noreply@cmu.dev`
   - Optionally set `FROM_NAME = ScottyLabs` or similar display name

4. **Restart Forgejo service**
   - `systemctl restart forgejo` (systemd)
   - OR `docker restart forgejo` (Docker)
   - OR appropriate command for deployment method

5. **Verify email delivery**
   - Trigger a test email (password reset, notification, etc.)
   - Check recipient inbox for email from `noreply@cmu.dev`
   - Verify SPF/DKIM/DMARC alignment if domain authentication is configured

6. **Update infrastructure documentation**
   - Document the sender address in relevant runbooks
   - Note any DNS records required for `cmu.dev` email authentication

## 6. Risks

### High-impact risks
- **Email authentication failure**: If `cmu.dev` SPF/DKIM records don't include the SMTP server, emails may be rejected or marked as spam
  - **Mitigation**: Verify DNS records before deployment; test with deliverability tools
  
- **SMTP relay rejection**: Some SMTP servers restrict which addresses can be used as `FROM`
  - **Mitigation**: Check with email provider; may need to whitelist `noreply@cmu.dev`

### Medium-impact risks

# Implementation Plan: Explore Alternatives to LiteLLM

## 1. Problem Analysis

### Current State
The Credit Conserver system currently uses a custom CLI wrapper around the `claude` binary (Claude Code) in `modules/anthropic_client.py`. This approach:
- Requires Claude Code to be installed and authenticated on the system
- Bypasses the official Anthropic SDK entirely
- Uses subprocess calls to invoke `claude -p` for all LLM interactions
- Has no actual LiteLLM dependency despite the issue title

### Problem Statement
The issue title "Explore alternatives to LiteLLM" suggests investigating different approaches for LLM integration. However, the codebase shows **no LiteLLM usage**. The real question is: **what's the best way to call Claude API in a GitHub Actions environment?**

Current options:
1. **Status quo**: CLI wrapper (requires Claude Code binary)
2. **Official Anthropic SDK**: Direct API calls
3. **LiteLLM**: Universal LLM proxy/wrapper
4. **Other**: Custom SDK wrappers, alternative libraries

### Why This Matters
- **Portability**: CLI approach requires Claude Code installation in CI
- **Token tracking**: Current estimation (`len(text) // 4`) is inaccurate
- **Rate limiting**: No native retry/backoff logic
- **Multi-model**: System uses dual-model strategy (Sonnet for plans, Haiku for commits)
- **Credit management**: Core feature requires accurate token counting

## 2. Technical Approach

### Strategy
Evaluate three primary approaches:

**Option A: Official Anthropic SDK** (RECOMMENDED)
- Direct API integration using `anthropic` Python package
- Accurate token counting via API response headers
- Built-in rate limiting, retries, streaming support
- Most lightweight dependency

**Option B: LiteLLM**
- Unified interface across multiple LLM providers
- Built-in fallbacks, load balancing, caching
- Overkill if only using Anthropic Claude

**Option C: Hybrid Approach**
- Keep CLI for local dev (leverages Claude Max subscription)
- Use SDK for GitHub Actions (uses API key)
- Requires environment detection logic

### Key Decision: Option A (Anthropic SDK)

**Rationale**:
- Single provider (Anthropic) = no need for universal wrapper
- Already in `requirements.txt` (imported by venv packages)
- Accurate token counting from API responses
- Better error handling than subprocess calls
- No external binaries required in CI

**Trade-offs**:
- Loses local Claude Max credit usage (requires API key always)
- More code changes than adding LiteLLM
- No multi-provider abstraction (not needed)

## 3. Implementation Steps

### Phase 1: Add Anthropic SDK Support
1. Update `requirements.txt` to explicitly include `anthropic>=0.18.0`
2. Create new `AnthropicSDKClient` class in `modules/anthropic_client.py`
3. Implement SDK-based methods matching existing interface:
   - `generate_plan()`
   - `generate_response()`
   - `generate_kernel_commit()`
   - `generate_pr_summary()`
4. Add accurate token tracking via `response.usage.input_tokens` / `output_tokens`

### Phase 2: Update Credit Tracker Integration
1. Modify return signatures to include actual token counts (not estimates)
2. Update `CreditTracker` to log actual vs estimated tokens
3. Add rate limit retry logic with exponential backoff
4. Handle `anthropic.RateLimitError` and `anthropic.APIError` properly

### Phase 3: Environment-Based Client Selection
1. Add `ANTHROPIC_API_KEY` environment variable check
2. If key present: use SDK client
3. If key absent and `claude` binary exists: use CLI wrapper
4. Add configuration option to force one mode or the other

### Phase 4: Update GitHub Actions Workflow
1. Add `ANTHROPIC_API_KEY` to GitHub Secrets (if not already present)
2. Update `.github/workflows/triage.yml` to pass API key
3. Remove any Claude Code installation steps (if present)

### Phase 5: Testing & Validation

2. Verify accurate token counting
3. Test rate limit handling
4. Compare credit usage: CLI estimates vs SDK actual
5. Run integration tests with real API

### Phase 6: Documentation & Migration

## 6. Risks & Unknowns

### High Risk
1. **API Key Cost**
   - CLI uses Claude Max subscription credits
   - SDK uses pay-per-use API credits
   - **Mitigation**: Document cost implications, make mode configurable

2. **Token Count Mismatch**
   - Current estimates (`len(text) // 4`) may differ significantly from actual
   - Could breach credit limits faster than expected
   - **Mitigation**: Add safety margin to credit caps during transition

### Medium Risk
1. **Rate Limiting**
   - SDK exposes real rate limits (CLI may not)
   - Could slow down parallel processing
   - **Mitigation**: Implement exponential backoff, add concurrency limits

2. **Breaking Changes**
   - Changing `anthropic_client.py` interface affects all callers
   - **Mitigation**: Keep old signatures, add internal conversion layer

### Low Risk
1. **GitHub Actions Setup**
   - Need to add API key secret to all repos
   - **Mitigation**: Document setup steps, provide example workflow

### Unknowns
1. **Claude Max vs API Feature Parity**
   - Are there differences in model capabilities?
   - Are rate limits different?
   - **Resolution**: Test both modes, document differences

2. **Actual Token Usage**
   - What's the real credit consumption?
   - How far off are current estimates?
   - **Resolution**: Run pilot with SDK logging both estimates and actuals

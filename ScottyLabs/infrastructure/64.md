# Implementation Plan: Migrate agenix to X-Wing Keys

## 1. Problem Analysis

### What Needs to Be Solved
Currently, agenix uses ssh-ed25519 keys for encrypting and decrypting secrets. The requirement is to migrate to X-Wing keys, a post-quantum cryptographic key exchange mechanism that combines X25519 (classical) with ML-KEM-768 (post-quantum) for hybrid security.

### Why This Change Is Needed
- **Post-quantum security**: X-Wing provides protection against both classical and quantum computing threats
- **Future-proofing**: Prepares infrastructure for the post-quantum cryptography era
- **Standardization**: X-Wing is an IETF draft standard combining proven classical and quantum-resistant algorithms
- **Hybrid approach**: Maintains security even if one algorithm is compromised

### Current State
- agenix uses Age encryption with ssh-ed25519 keys
- Hosts have ssh-ed25519 host keys
- Users have ssh-ed25519 user keys
- Secrets are encrypted with Age using recipients derived from SSH keys

### Desired State
- All hosts provisioned with X-Wing keys
- All users expected to have X-Wing keys
- Secrets encrypted with Age using X-Wing key format
- Backward compatibility during transition period

## 2. Technical Approach

### Strategy
**Phased migration with backward compatibility**

1. **Phase 1: Infrastructure preparation**
   - Add X-Wing key support to agenix
   - Create tooling for X-Wing key generation and management
   - Update Age configuration to support X-Wing recipients

2. **Phase 2: Key provisioning**
   - Generate X-Wing keys for all hosts
   - Distribute X-Wing key generation instructions/tooling to users
   - Maintain ssh-ed25519 keys during transition

3. **Phase 3: Secret re-encryption**
   - Dual-encrypt secrets (both ssh-ed25519 and X-Wing)
   - Verify decryption works with both key types
   - Monitor adoption across hosts/users

4. **Phase 4: Deprecation**
   - Remove ssh-ed25519 recipients from secrets
   - Remove ssh-ed25519 key handling from agenix
   - Document X-Wing-only workflow

### Key Technical Decisions

**Decision 1: X-Wing Implementation Library**
- **Option A**: Use `rage` (Rust Age implementation) if it supports X-Wing
- **Option B**: Use custom Age plugin for X-Wing
- **Option C**: Patch Age/rage to add X-Wing support
- **Recommendation**: Option A if available, otherwise Option B (plugin system maintains Age compatibility)

**Decision 2: Key Storage Format**
- **Option A**: Store X-Wing keys in Age format (`.age` files)
- **Option B**: Store in custom format with metadata
- **Recommendation**: Option A (consistent with existing agenix key handling)

**Decision 3: Transition Strategy**
- **Option A**: Hard cutover (all at once)
- **Option B**: Dual-encryption during transition
- **Option C**: Per-secret migration flags
- **Recommendation**: Option B (safest, allows gradual rollout, rollback possible)

**Decision 4: Host Key Generation**
- **Option A**: Generate during NixOS rebuild (deterministic)
- **Option B**: Generate during initial provisioning (pre-install)
- **Option C**: Manual generation + deployment
- **Recommendation**: Option A for reproducibility, Option B for bootstrapping new hosts

## 3. Implementation Steps

### Step 1: Research and Validate X-Wing Support
1. Verify Age/rage X-Wing support status
2. Identify X-Wing key generation tooling (e.g., `age-plugin-xwing`)
3. Test X-Wing key generation and Age encryption/decryption locally
4. Document Age CLI commands for X-Wing operations

### Step 2: Extend agenix for X-Wing Key Format
1. Update `agenix` Nix module to recognize X-Wing public key format
2. Add X-Wing key type detection (e.g., by prefix or file extension)
3. Modify `agenix` encryption logic to support X-Wing recipients
4. Update `agenix` CLI tool to handle X-Wing key file paths

### Step 3: Create Host Key Generation Module
1. Create NixOS module `services.agenix-xwing-keys.nix`
2. Add option to auto-generate X-Wing host keys on first boot
3. Store keys in `/etc/agenix/xwing-host.key` (private) and `/etc/agenix/xwing-host.pub` (public)
4. Set appropriate permissions (600 for private, 644 for public)
5. Add systemd service to generate key if missing

### Step 4: Create User Key Generation Tooling
1. Create script `agenix-xwing-keygen` for user key generation
2. Package script as Nix derivation
3. Add to system packages or provide as standalone tool
4. Include instructions in documentation

### Step 5: Update Secret Encryption Workflow
1. Modify `.age` secret files to include both ssh-ed25519 and X-Wing recipients
2. Create script to batch-reencrypt all secrets with dual recipients
3. Test decryption with both key types across test hosts
4. Document new `agenix -e secret.age` workflow

### Step 6: Update NixOS Configurations
1. Add X-Wing public keys to host configurations
2. Update `age.secrets.<name>.publicKeys` to include X-Wing keys
3. Add user X-Wing public keys to recipient lists
4. Deploy to staging hosts first

### Step 7: Validate and Monitor
1. Deploy to canary hosts
2. Monitor secret decryption success rates
3. Verify services dependent on secrets start correctly
4. Test user access to secrets with X-Wing keys

### Step 8: Full Rollout
1. Deploy X-Wing key generation to all hosts
2. Communicate X-Wing key requirement to all users
3. Provide deadline for ssh-ed25519 deprecation
4. Monitor adoption metrics

### Step 9: Remove ssh-ed25519 Support
1. Remove ssh-ed25519 public keys from secret recipient lists
2. Re-encrypt all secrets with X-Wing recipients only
3. Remove ssh-ed25519 key handling code from agenix module
4. Update documentation to X-Wing-only workflow

### Step 10: Cleanup
1. Remove old ssh-ed25519 keys from host configurations
2. Archive migration scripts
3. Update README and deployment documentation
4. Remove transition-period code paths

## 6. Risks

### Technical Risks
**Risk 1: X-Wing Support Unavailable in Age/rage**
- **Likelihood**: Medium
- **Impact**: High (blocks entire migration)
- **Mitigation**: Research before implementation, identify Age plugin architecture, consider custom plugin development
- **Fallback**: Use alternative post-quantum algorithm supported by Age (e.g., ML-KEM directly)

**Risk 2: Performance Degradation**
- **Likelihood**: Low
- **Impact**: Medium
- **Mitigation**: Benchmark X-Wing encryption/decryption vs ssh-ed25519, test on production-scale secret files
- **Threshold**: <100ms additional latency acceptable for secret decryption

**Risk 3: Key Generation Non-Determinism**
- **Likelihood**: Medium
- **Impact**: Medium (complicates NixOS reproducibility)
- **Mitigation**: Generate keys during provisioning, not during build; store in mutable state directory
- **Alternative**: Deterministic key derivation from host-specific seed (research required)

**Risk 4: Incompatibility with Existing agenix Tooling**
- **Likelihood**: Medium
- **Impact**: High (breaks existing workflows)
- **Mitigation**: Maintain backward compatibility during transition, extensive testing with dual-key setup
- **Fallback**: Fork agenix if upstream doesn't support X-Wing

### Operational Risks
**Risk 5: User Adoption Friction**
- **Likelihood**: High
- **Impact**: Medium
- **Mitigation**: Provide clear documentation, simple tooling, support window with dual-key access
- **Plan**: 30-day transition period before ssh-ed25519 deprecation

**Risk 6: Secret Decryption Failures During Migration**
- **Likelihood**: Medium
- **Impact**: Critical (service outages)
- **Mitigation**: Maintain dual-recipient encryption, test extensively in staging, phased rollout with canary hosts
- **Rollback**: Keep ssh-ed25519 keys active until 100% X-Wing adoption confirmed

**Risk 7: Lost Private Keys**
- **Likelihood**: Low
- **Impact**: Critical (permanent secret loss)
- **Mitigation**: Backup all private keys securely, document key recovery procedures, maintain multiple recipient keys per secret
- **Prevention**: Require minimum 2 recipients per secret (e.g., admin + service)

### Dependency Risks
**Risk 8: Age/rage Version Compatibility**
- **Likelihood**: Medium
- **Impact**: Medium
- **Mitigation**: Pin specific Age/rage version in Nix, test with multiple versions, document minimum version requirements
- **Monitoring**: Track Age/rage updates for X-Wing support changes

**Risk 9: X-Wing Standard Evolution**
- **Likelihood**: Low
- **Impact**: High (re-migration required)
- **Mitigation**: Follow IETF draft status, plan for re-keying if standard changes materially
- **Timeline**: Monitor X-Wing RFC progression quarterly

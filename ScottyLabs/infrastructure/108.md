# Implementation Plan: Replace Org-Level CI Secrets with SecretSpec Action

## 1. Problem Analysis

### Current State
- Organization-level CI secrets are currently managed via Terraform using `resource.forgejo_organization_action_secret` blocks in `governance.nix`
- These secrets are long-lived and stored statically
- Requires manual rotation and management
- Secrets are defined at the organization level and available to all repositories

### Target State
- Use OpenBao's OIDC provider to issue short-lived JWT tokens
- Leverage Forgejo/Gitea Actions' built-in OIDC feature (`ACTIONS_ID_TOKEN_REQUEST_URL`, `ACTIONS_ID_TOKEN_REQUEST_TOKEN`)
- Replace static secrets with a secretspec action that dynamically fetches credentials on each workflow run
- Tokens automatically expire, reducing security risk
- No manual rotation required

### Why This Matters
- **Security**: Short-lived tokens reduce blast radius if leaked
- **Automation**: No manual secret rotation needed
- **Auditability**: OpenBao provides centralized audit logs for token issuance
- **Infrastructure-as-Code**: Remove secret values from Terraform state

## 2. Technical Approach

### Strategy
1. Create a reusable GitHub/Forgejo Action (`secretspec-action`) that:
   - Reads OIDC token from CI environment
   - Exchanges it with OpenBao for short-lived credentials
   - Exports credentials as environment variables or outputs
2. Configure OpenBao to trust Forgejo's OIDC issuer
3. Remove `resource.forgejo_organization_action_secret` blocks from `governance.nix`
4. Update workflow files to use the secretspec action instead of org secrets

### Key Decisions

**Action Implementation**
- Language: Shell script (minimal dependencies) or TypeScript/composite action
- Distribution: Git repository with versioned releases (`v1`, `v1.0.0`)
- Configuration: Action inputs for OpenBao URL, role, secret path

**OpenBao Configuration**
- JWT auth method configured with Forgejo's OIDC issuer
- Role bindings based on repository/organization/workflow claims
- Policy attachments for secret access scoped per use case

**Migration Path**
- Dual-run period: Keep org secrets while testing secretspec action
- Per-repo migration: Update workflows one at a time
- Deprecation: Remove org secrets only after all workflows migrated

## 3. Implementation Steps

### Step 1: Configure OpenBao JWT Auth Backend
1. Enable JWT auth method in OpenBao
2. Configure OIDC discovery URL to point to Forgejo instance
3. Set bound issuer, audience claims
4. Create example role with policy bindings

**Acceptance**: `openbao write auth/jwt/config` succeeds, OIDC metadata validates

### Step 2: Create SecretSpec Action Repository
1. Initialize new Git repository for the action
2. Create `action.yml` manifest with inputs:
   - `openbao_url` (required)
   - `openbao_role` (required)
   - `secret_path` (required)
   - `export_env` (optional, boolean, default true)
3. Implement action script:
   - Read `ACTIONS_ID_TOKEN_REQUEST_TOKEN` and `ACTIONS_ID_TOKEN_REQUEST_URL`
   - Request OIDC token from Forgejo
   - Authenticate to OpenBao using JWT
   - Fetch secrets from specified path
   - Export as environment variables or action outputs
4. Add error handling (missing env vars, network failures, auth failures)
5. Tag initial release `v1.0.0`

**Acceptance**: Action runs successfully in test workflow, exports dummy secrets

### Step 3: Update Governance.nix
1. Locate all `resource.forgejo_organization_action_secret` blocks
2. Document which secrets are being replaced (create migration table)
3. Comment out blocks (do not delete yet) with migration date
4. Add OpenBao role and policy definitions corresponding to removed secrets

**Acceptance**: Terraform plan shows deletions for org secrets, new OpenBao resources created

### Step 4: Migrate Workflows
1. Identify all workflow files using org secrets (grep for `secrets.`)
2. For each workflow:
   - Add secretspec action step before secret usage
   - Replace `${{ secrets.FOO }}` with `${{ steps.secretspec.outputs.FOO }}` or `$FOO` env var
   - Test workflow run
3. Update workflow documentation

**Acceptance**: All workflows run successfully with secretspec action, no references to org secrets remain

### Step 5: Cleanup
1. Remove commented-out `resource.forgejo_organization_action_secret` blocks from `governance.nix`
2. Apply Terraform to delete org secrets
3. Archive or delete OpenBao backup of old secrets

**Acceptance**: `terraform state list` shows no `forgejo_organization_action_secret` resources

### Integration Tests

## 6. Risks

### Technical Risks

**Risk**: Forgejo OIDC feature not available or misconfigured
- **Mitigation**: Verify Forgejo version supports `ACTIONS_ID_TOKEN_REQUEST_URL`
- **Workaround**: Use long-lived service account token as fallback

**Risk**: OpenBao JWT issuer validation fails due to TLS/cert issues
- **Mitigation**: Test OIDC discovery URL accessibility from OpenBao instance
- **Workaround**: Configure explicit JWKS URL instead of discovery

**Risk**: Token expiration causes long-running workflows to fail
- **Mitigation**: Set appropriate TTL (default: workflow duration + buffer)
- **Workaround**: Add token refresh logic to action

**Risk**: Circular dependency - secretspec action needs secrets to bootstrap
- **Mitigation**: OpenBao URL and role are not secrets, passed as plain inputs
- **Workaround**: Use Kubernetes service account or instance metadata for initial auth

### Operational Risks

**Risk**: All workflows break if OpenBao is down
- **Mitigation**: High availability OpenBao deployment
- **Workaround**: Keep one critical org secret as emergency fallback

**Risk**: Debugging workflow failures harder with dynamic secrets
- **Mitigation**: Add verbose logging to secretspec action (redact secret values)
- **Workaround**: OpenBao audit logs provide token issuance trail

**Risk**: Team unfamiliar with OIDC/JWT workflows
- **Mitigation**: Comprehensive documentation and examples
- **Workaround**: Runbook for common failure scenarios

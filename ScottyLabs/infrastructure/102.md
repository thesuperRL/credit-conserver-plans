# Implementation Plan: Document Observability Platform

## 1. Problem Analysis

### Current State
The Credit Conserver project currently has **no observability infrastructure**:
- Only basic stdout logging via `utils.log()` (timestamp + level + message)
- No error tracking (Sentry)
- No metrics collection (Prometheus)
- No distributed tracing (Tempo)
- No log aggregation (Loki)
- No visualization (Grafana)

### What Needs to Be Solved
Issue #102 requests:
1. **Documentation** explaining the relationship between:
   - **Sentry**: Error tracking and alerting
   - **Prometheus/Tempo/Grafana/Loki** (PTGL): Full observability stack
2. **Setup guide** for running both systems together
3. **Shared instrumentation code**: Reusable Rust crate + TypeScript package

### Why This Matters
- **Sentry** provides real-time error alerts, user impact tracking, and release health
- **PTGL stack** provides deep operational visibility: metrics dashboards, trace timelines, log search
- **Duplication concern**: Both collect telemetry; overlapping responsibilities need clarification
- **Multi-language support**: Python bot today, but Rust/TS may be future components

## 2. Technical Approach

### Key Decisions

**Decision 1: Document, Don't Implement**  
The issue asks to "document" and "explain duplication" - not to instrument the existing Python codebase. The plan focuses on:
- Creating `docs/OBSERVABILITY.md` explaining the relationship
- Providing setup examples
- Stubbing out shared libraries (not full implementation)

**Decision 2: Lazy Shared Libraries**  
Per ponytail mode, the "shared crate/package" will be:
- **Minimal stubs** showing structure, not full SDKs
- Use **official SDKs** directly (`sentry-sdk`, `sentry-python`, Prometheus client libs)
- Shared code only for **configuration patterns**, not reinventing instrumentation

**Decision 3: Architecture Patterns**
- **Sentry for errors**: Exception capture, breadcrumbs, user context
- **PTGL for operations**: Request rates, latency histograms, trace waterfalls, log search
- **Overlap**: Both can capture logs/errors → document when to use each
- **Integration**: Sentry can export to Prometheus; Grafana can query both

### Stack Relationship

```
┌─────────────────────────────────────────────────────────────┐
│                        Grafana (Visualization)              │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐         │
│  │ Prometheus  │  │    Tempo    │  │    Loki     │         │
│  │  (Metrics)  │  │  (Traces)   │  │   (Logs)    │         │
│  └─────────────┘  └─────────────┘  └─────────────┘         │
└─────────────────────────────────────────────────────────────┘
                              │
                              │ (optional export)
                              ▼
                    ┌─────────────────┐
                    │     Sentry      │
                    │ (Errors/Alerts) │
                    └─────────────────┘
```

**Use Sentry when:**
- You want instant Slack/email alerts on exceptions
- Tracking error frequency across releases
- Grouping duplicate errors automatically
- Need browser/mobile SDK integration

**Use PTGL when:**
- Building custom metrics dashboards
- Tracing request flows across services
- Searching logs with complex queries
- Self-hosted infrastructure preferred

**Use both when:**
- Sentry for alerting + user impact
- PTGL for deep operational analysis
- Cross-reference: Sentry issue → Tempo trace ID

## 6. Risks and Blockers

### Risk: Scope Creep
**Mitigation**: Issue asks to "document" and create "shared packages" - not to fully instrument the bot. Stick to documentation + minimal stubs using official SDKs.

### Risk: Rust/TS Packages May Never Be Used
**Mitigation**: Keep them **minimal** (< 100 lines each). If this project stays Python-only, they document the pattern for future polyglot work.

### Risk: PTGL Stack Complexity
**Mitigation**: Docker Compose handles orchestration. Provide a "quick start" that works out-of-the-box with zero config beyond `docker-compose up`.

### Risk: Sentry Pricing (SaaS)
**Mitigation**: Document both SaaS and self-hosted options. Default examples use self-hosted or free tier.

### Unknown: What "Duplication" Means
**Clarification needed**: Does the user mean:
1. Sentry AND PTGL both collect logs/errors (wasteful)?
2. Multiple instrumentation codebases (Rust + TS + Python)?
3. Something else?

**Assumption**: Interpreting as "explain when to use Sentry vs PTGL vs both" + "create reusable config code".

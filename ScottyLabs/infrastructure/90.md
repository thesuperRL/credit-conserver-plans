# Implementation Plan: Set up actions for `git.cmu.dev`

## 1. Problem Analysis

### What Needs to Be Solved
- Add support for CMU's self-hosted Gitea instance (`git.cmu.dev`) as a new platform
- Enable the Credit Conserver bot to process issues and create PRs on CMU repositories
- Maintain compatibility with existing GitHub and Codeberg platforms

### Why This Matters
- CMU uses a self-hosted Gitea instance that's functionally similar to Codeberg
- The existing Codeberg implementation (Gitea API) can be reused with minimal changes
- This enables the bot to work across CMU's internal repositories

### Current State
- The system supports GitHub (PyGithub) and Codeberg (Gitea REST API)
- Platform abstraction via `GitPlatform` interface is in place
- `PlatformManager` handles multi-platform client initialization
- Repository format: `platform:owner/repo` (e.g., `codeberg:user/project`)

## 2. Technical Approach

### Strategy
**Reuse existing Gitea implementation** - Since `git.cmu.dev` is a Gitea instance (like Codeberg), we can leverage the existing `CodebergPlatform` class with a custom API URL rather than creating an entirely new platform implementation.

### Key Design Decisions
1. **New platform identifier**: Add `"cmu"` as a platform type
2. **Reuse Gitea client**: Extend or alias `CodebergPlatform` for CMU
3. **Configuration approach**: Add CMU-specific token and API URL to config
4. **API URL**: `https://git.cmu.dev/api/v1` (standard Gitea v1 endpoint)

### Alternative Considered (Rejected)
- Creating a separate `CMUPlatform` class would duplicate ~200 lines of Gitea REST API code
- **Rejection reason**: YAGNI - the API is identical, only the base URL differs

## 6. Risks & Mitigations

### Risk 1: CMU Gitea API Version Mismatch
**Impact**: Medium  
**Probability**: Low  
**Description**: CMU might run a different Gitea version with API incompatibilities  
**Mitigation**: Test against actual CMU instance; Gitea v1 API is stable across versions

### Risk 2: Authentication Differences
**Impact**: Medium  
**Probability**: Low  
**Description**: CMU might use different authentication (OAuth vs token)  
**Mitigation**: Standard Gitea token auth should work; document fallback to SSH

### Risk 3: Rate Limits
**Impact**: Low  
**Probability**: Medium  
**Description**: Self-hosted instances may have stricter rate limits  
**Mitigation**: Existing rate limit handling in `CodebergPlatform` should catch this

### Risk 4: Network Access
**Impact**: High  
**Probability**: Low (if running in GitHub Actions)  
**Description**: GitHub Actions runners might not reach internal CMU network  
**Mitigation**: Use publicly accessible `git.cmu.dev`; if internal-only, document self-hosted runner requirement

### Risk 5: Token Permissions
**Impact**: Medium  
**Probability**: Medium  
**Description**: CMU token might lack required scopes (repo write, PR creation)  
**Mitigation**: Document required scopes in DEPLOYMENT.md; test token permissions before first run

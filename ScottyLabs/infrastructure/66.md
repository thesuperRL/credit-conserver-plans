# Implementation Plan: Use preservation on signage-01

## 1. Problem Analysis

### What needs to be solved
The signage-01 system is a NixOS digital signage display that currently does not use the `preservation` tool from nix-community. This means that important stateful data (configuration files, service state, logs, credentials) may be lost during system rebuilds or redeployments.

### Why it matters
- **Data loss risk**: Without preservation, system state is ephemeral and rebuilds wipe important data
- **Manual recovery overhead**: Operators must manually restore state after rebuilds
- **Deployment friction**: Fear of data loss makes system updates risky and infrequent
- **Infrastructure-as-code gap**: State management is not declarative, breaking the NixOS reproducibility model

### Current state
- signage-01 is managed in the ScottyLabs/infrastructure Codeberg repository
- The system likely has stateful services (display configuration, credentials, logs) that need preservation
- No preservation module is currently configured

## 2. Technical Approach

### Strategy
1. **Add preservation as a flake input** to the infrastructure repository
2. **Import the preservation NixOS module** in the signage-01 host configuration
3. **Audit signage-01 for stateful data** that needs preservation (configs, credentials, service data, logs)
4. **Configure preservation declaratively** using the preservation.preserveAt option
5. **Choose a persistence mount point** (typically `/persist` or `/var/persist`)
6. **Set up initial state migration** to move existing state into the preserved directory structure

### Key decisions

**Persistence mount point**: Use `/persist` as the preservation root
- Standard convention in NixOS community
- Clean separation from system root
- Easy to identify preserved vs ephemeral data

**What to preserve**:
- Service-specific state directories (e.g., `/var/lib/<service>`)
- Machine identity files (`/etc/machine-id`, SSH host keys)
- Application configuration that's not in Nix
- Logs if they need to persist across rebuilds
- Credentials and secrets

**What NOT to preserve**:
- Anything already managed by Nix configuration
- Temporary files and caches
- System state that should be rebuilt fresh

**Migration approach**:
- One-time manual migration of existing state to `/persist` structure
- Document the migration process for operators
- Consider a backup before the first rebuild with preservation

## 3. Implementation Steps

### Step 1: Add preservation to flake inputs
- Locate the root `flake.nix` in ScottyLabs/infrastructure
- Add `preservation.url = "github:nix-community/preservation";` to inputs
- Add preservation to the outputs function parameters
- Update flake.lock by running `nix flake update preservation`

### Step 2: Identify signage-01 configuration file
- Find the NixOS configuration file for signage-01 (likely `hosts/signage-01/default.nix` or similar)
- Review existing module imports

### Step 3: Import preservation module
- Add `preservation.nixosModules.preservation` to the host's module imports
- Can be added at the host level or in a shared configuration

### Step 4: Audit signage-01 for stateful data
- SSH to signage-01 or review its current configuration
- Identify directories in `/var/lib/`, `/etc/`, and other locations that contain state
- Common candidates for digital signage:
  - Display manager state
  - Network configuration
  - SSH host keys (`/etc/ssh/ssh_host_*`)
  - Machine ID (`/etc/machine-id`)
  - Service-specific state (logs, credentials, configs)
  - User home directories if applicable

### Step 5: Configure preservation
Add to signage-01 configuration:

```nix
{
  preservation = {
    enable = true;
    preserveAt."/persist" = {
      directories = [
        # Identified in Step 4
        "/var/lib/systemd"
        "/var/lib/<display-service>"
        # Add all stateful directories
      ];
      files = [
        "/etc/machine-id"
        "/etc/ssh/ssh_host_rsa_key"
        "/etc/ssh/ssh_host_rsa_key.pub"
        "/etc/ssh/ssh_host_ed25519_key"
        "/etc/ssh/ssh_host_ed25519_key.pub"
        # Add all stateful files
      ];
    };
  };
}
```

### Step 6: Create /persist mount point
- Add filesystem configuration to ensure `/persist` is on persistent storage
- If using tmpfs root, ensure `/persist` is a separate partition or bind mount to persistent storage

### Step 7: Document migration procedure
Create a migration runbook:
1. Back up current state: `tar czf /root/pre-preservation-backup.tar.gz /var/lib /etc/ssh /etc/machine-id`
2. Create `/persist` directory structure matching preservation config
3. Copy existing state to `/persist` locations
4. Deploy the new configuration with preservation enabled
5. Verify services start correctly with preserved state
6. Test a rebuild to confirm state persists

### Step 8: Test on a non-production system first
- If possible, test the configuration on a similar system or VM
- Verify state actually persists across a rebuild
- Adjust the preserved files/directories list as needed

### Step 9: Deploy to signage-01
- Schedule maintenance window
- Execute migration procedure
- Deploy new configuration
- Verify all services operational
- Test rebuild to confirm persistence works

### Step 10: Update documentation
- Add preservation configuration to infrastructure documentation
- Document what is preserved and why
- Document migration procedure for future reference
- Add to disaster recovery procedures

## 5. Testing Strategy

### Pre-deployment testing
1. **Nix evaluation check**: `nix flake check` to ensure configuration is valid
2. **Build test**: `nixos-rebuild build --flake .#signage-01` to ensure configuration builds
3. **VM test** (if feasible): Deploy to a VM and test state persistence across rebuilds

### Deployment verification
1. **Service health check**: Verify all services start correctly after initial deployment
2. **State presence check**: Confirm preserved files and directories exist in `/persist`
3. **Rebuild test**: Perform a `nixos-rebuild switch` and verify state persists

### Post-deployment monitoring
1. **Service continuity**: Monitor that services continue running without state loss
2. **Log review**: Check system logs for preservation-related errors
3. **Rebuild testing**: Periodically test system rebuilds to ensure preservation continues working

### Rollback plan
1. Keep backup from pre-migration state
2. If issues occur, can rebuild without preservation module
3. Restore state from backup if necessary
4. Document issues for fixing before retry

**Impact**: High  
**Mitigation**:

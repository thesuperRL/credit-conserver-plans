# Implementation Plan: ForgeSync - Forgejo Platform Support

## 1. Problem Analysis

### What needs to be solved
Add support for Forgejo (self-hosted Git forge) to the multi-platform agentic planning system, enabling issue management, pull request workflows, and project board integration with Forgejo instances.

### Why it matters
- **Multi-platform completeness**: System already supports GitHub and Codeberg; Forgejo is a major open-source forge alternative
- **Self-hosted requirements**: Teams using Forgejo need the same agentic planning capabilities
- **API compatibility**: Forgejo is a Gitea fork with similar API, making integration straightforward
- **Consistency**: Users expect uniform behavior across all supported platforms

### Current state
- Existing implementations: `github_platform.py`, `codeberg_platform.py`
- Base interface: `git_platform.py` (abstract base class)
- Platform manager handles routing between implementations
- Config system supports multiple platform types

## 2. Technical Approach

### Strategy
**Clone-and-adapt pattern** - Forgejo API is nearly identical to Gitea/Codeberg APIs, so:
1. Use `codeberg_platform.py` as template (Codeberg uses Gitea under the hood)
2. Add Forgejo-specific configuration (base URL, token handling)
3. Implement platform-agnostic URL construction for self-hosted instances
4. Register in platform manager and config system

### Key decisions
- **API compatibility**: Use Gitea-compatible API endpoints (Forgejo is Gitea-based)
- **Authentication**: API token via headers (`Authorization: token <TOKEN>`)
- **Base URL handling**: Support custom instance URLs (e.g., `https://forge.example.com`)
- **Minimal divergence**: Only override where Forgejo differs from Codeberg/Gitea

### Trade-offs
- ✅ **Fast implementation**: Reuse 90% of Codeberg implementation
- ✅ **Low risk**: Well-tested API patterns
- ⚠️ **Future divergence**: Forgejo/Gitea may diverge; monitor API changes
- ⚠️ **Self-hosted variance**: Different instances may have different versions/features

## 6. Risks & Unknowns

### Known Risks
- **API version differences**: Forgejo may use different Gitea API version
  - *Mitigation*: Check Forgejo version in instance response, log warnings
  - *Fallback*: Document minimum supported Forgejo version

- **Self-hosted SSL issues**: Some instances may have self-signed certs
  - *Mitigation*: Add `verify_ssl` config option (default=True)
  - *Document*: SSL troubleshooting in MULTI_PLATFORM.md

- **Rate limiting**: Self-hosted instances may have different limits
  - *Mitigation*: Reuse existing retry logic from base class
  - *Enhancement*: Make backoff configurable

### Unknowns
- **Forgejo-specific features**: Newer features not in Gitea
  - *Discovery*: Review Forgejo changelog vs Gitea
  - *Action*: Only use common API surface for v1

- **Project board API**: May differ from Gitea/Codeberg
  - *Investigation*: Test against Forgejo instance
  - *Fallback*: Disable project board features if incompatible

- **Webhook formats**: For future webhook integration
  - *Defer*: Out of scope for initial implementation

### Blockers
- ❌ **No public Forgejo instance for testing**: Most are self-hosted
  - *Resolution*: Use Docker-based local instance for testing
  - *Alternative*: Use Codeberg (Gitea-based) as compatibility proxy

- ⚠️ **Token permissions unclear**: Scope requirements unknown
  - *Resolution*: Document in MULTI_PLATFORM.md after manual testing
  - *Minimum*: Likely needs `repo` and `write:discussion` scopes

# Implementation Plan: Provision `git.cmu.dev` OAuth Client in Terranix

## Problem Analysis

### What needs to be solved
The ScottyLabs infrastructure repository needs to provision an OAuth application for `git.cmu.dev` (a self-hosted Git platform, likely Gitea/Forgejo) using terranix (Nix-based Terraform configuration). This OAuth client will enable third-party applications to authenticate users via git.cmu.dev.

### Why it's needed
- **Service Integration**: Enable external services to authenticate against git.cmu.dev
- **Infrastructure as Code**: Manage OAuth clients declaratively through terranix instead of manual web UI configuration
- **Reproducibility**: Version-controlled OAuth client configuration that can be rebuilt/redeployed
- **Automation**: Part of broader infrastructure automation efforts

## Technical Approach

### Strategy
1. Use terranix to generate Terraform configuration in Nix
2. Leverage the Gitea Terraform provider to manage OAuth applications
3. Store sensitive OAuth secrets in appropriate secret management (likely sops-nix or similar)
4. Follow existing terranix patterns in the infrastructure repository

### Key Decisions
- **Provider**: Use `terraform-provider-gitea` for Gitea/Forgejo OAuth management
- **Secret Management**: Store client secrets securely, reference via Nix secrets mechanism
- **Callback URLs**: Define as configurable parameters in terranix config
- **Naming Convention**: Follow ScottyLabs naming patterns (likely `scottylabs-<service>`)

## Implementation Steps

### 1. Research existing infrastructure patterns
- Read existing terranix configurations in ScottyLabs/infrastructure repo
- Identify secret management approach (sops-nix, agenix, vault, etc.)
- Note naming conventions and module organization

### 2. Add Gitea Terraform provider to terranix
- Import `terraform-provider-gitea` in terranix configuration
- Configure provider with git.cmu.dev API endpoint
- Set up authentication (likely personal access token stored as secret)

### 3. Define OAuth client resource
```nix
# Pseudocode structure
resource.gitea_oauth2_app."git-cmu-dev-oauth" = {
  name = "ScottyLabs OAuth Client";
  redirect_uris = [
    "https://example.scottylabs.org/callback"
    # Additional callback URLs
  ];
  confidential_client = true; # or false for public clients
  scopes = ["read:user" "read:email"]; # Adjust based on needs
};
```

### 4. Output OAuth credentials
- Export `client_id` as Terraform output
- Store `client_secret` in secret management system
- Document how consuming services retrieve these values

### 5. Documentation
- Add README section on OAuth client usage
- Document callback URL management process
- Provide example integration code snippets

### 6. Apply and verify
- Run `terranix` to generate Terraform config
- Run `terraform plan` to preview changes
- Apply with `terraform apply`
- Verify OAuth app appears in git.cmu.dev admin panel

## Files to Modify

### New Files to Create
1. **`oauth-clients/git-cmu-dev.nix`** (or similar path)
   - Terranix module defining the OAuth client resource
   - Configurable parameters (name, redirect URIs, scopes)

2. **`secrets/oauth-git-cmu-dev.yaml`** (if using sops-nix)
   - Encrypted secrets file containing provider authentication token

### Existing Files to Modify
1. **`default.nix`** or **`flake.nix`** (root infrastructure config)
   - Import new OAuth client module
   - Add to terranix module list

2. **`terraform-providers.nix`** (or equivalent)
   - Add `terraform-provider-gitea` to provider list
   - Configure provider version pinning

3. **`README.md`**
   - Document OAuth client provisioning process
   - Add section on managing callback URLs

4. **`.sops.yaml`** or equivalent (if using sops-nix)
   - Add new secret paths for OAuth credentials

## Testing Strategy

### Manual Verification
1. **Provider connectivity**: Verify Terraform can authenticate to git.cmu.dev API
2. **Resource creation**: Confirm OAuth app is created in git.cmu.dev UI
3. **Idempotency**: Run `terraform plan` again, should show no changes
4. **Credentials**: Verify client_id and client_secret are retrievable

### Integration Testing
1. **OAuth flow**: Test full OAuth authorization flow with a test application
   - Authorization request redirects correctly
   - Token exchange succeeds
   - User info endpoint returns expected data
2. **Callback URLs**: Verify all configured callback URLs work
3. **Scopes**: Confirm granted scopes match requested scopes

### Destruction Testing
1. Run `terraform destroy` to clean up
2. Verify OAuth app is removed from git.cmu.dev
3. Re-apply to confirm reproducibility

## Risks

### Blockers
- **Unknown infrastructure repository structure**: May need to adapt to existing patterns not visible from this repository
- **Gitea provider availability**: Terraform provider for Gitea may have limitations or bugs
- **Secret management integration**: Specific secret manager used (sops-nix, agenix, etc.) will dictate implementation details
- **API access**: May need elevated permissions on git.cmu.dev to manage OAuth apps via API

### Unknowns
- **Exact terranix version/modules** in use
- **Current secret management system**
- **Existing OAuth clients** that may serve as reference examples
- **Required OAuth scopes** for the intended consuming service
- **git.cmu.dev version** (Gitea vs Forgejo, version number affects API compatibility)

### Mitigation
- Start by reading existing infrastructure code thoroughly
- Test in a staging/dev environment if available
- Use Terraform's state backup features before applying
- Document all assumptions for future maintainers

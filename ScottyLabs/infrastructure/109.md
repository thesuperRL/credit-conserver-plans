# Implementation Plan: Explore `nixos-unified` as Alternative to `flake-parts` and `colmena`

## 1. Problem Analysis

### What needs to be solved
The current NixOS configuration likely uses:
- **`flake-parts`**: A modular framework for organizing Nix flakes into reusable components
- **`colmena`**: A deployment tool for managing multiple NixOS machines

**Why explore `nixos-unified`:**
- **Reduced complexity**: Single tool instead of two separate frameworks
- **Integrated approach**: `nixos-unified` provides both configuration organization AND deployment in one cohesive system
- **Better ergonomics**: Simplified syntax and less boilerplate compared to `flake-parts`
- **Active development**: Modern approach with good community momentum
- **Type safety**: Better validation of configuration structure

### Current pain points likely being addressed
1. `flake-parts` boilerplate overhead for simple configurations
2. Managing two separate tools (`flake-parts` + `colmena`) with different paradigms
3. Complexity in organizing multi-host configurations
4. Deployment workflow friction between configuration and deployment layers

## 2. Technical Approach

### Strategy
**Phase 1: Evaluation** (read-only exploration)
- Create parallel `nixos-unified` configuration without touching existing setup
- Compare feature parity, ergonomics, and deployment workflows
- Document pros/cons and migration complexity

**Phase 2: Migration** (if evaluation is positive)
- Incremental conversion: one host at a time
- Keep existing config as fallback during transition
- Validate each migration step with test deployments

**Phase 3: Cleanup** (post-migration)
- Remove `flake-parts` and `colmena` dependencies
- Consolidate configuration structure
- Update documentation

### Key decisions
1. **Migration approach**: Incremental (safe) vs. big-bang (risky)
   - **Decision**: Incremental, one host at a time
2. **Evaluation timeframe**: How long to run both systems in parallel
   - **Decision**: Minimum one successful deployment cycle per host
3. **Rollback strategy**: Keep old config or delete immediately
   - **Decision**: Keep in git history via branch, don't maintain dual configs long-term
4. **Testing**: How to validate without breaking production
   - **Decision**: Use VM tests and staging hosts first

## 3. Implementation Steps

### Step 1: Research & Setup (1-2 hours)
1. Read `nixos-unified` documentation and examples
2. Review current `flake-parts` and `colmena` usage patterns
3. Create feature comparison matrix
4. Clone repo to experimental branch `explore/nixos-unified`

### Step 2: Create Parallel Configuration (2-4 hours)
1. Add `nixos-unified` to flake inputs
2. Create minimal `nixos-unified` configuration for one test host
3. Port existing host configuration to `nixos-unified` format
4. Verify it builds: `nix flake check` and `nix build`

### Step 3: Test Deployment Workflow (1-2 hours)
1. Deploy to VM using `nixos-unified`
2. Compare deployment process with `colmena`
3. Test rollback capabilities
4. Document deployment command differences

### Step 4: Feature Parity Check (2-3 hours)
1. Verify all current features work in `nixos-unified`:
   - Multi-host support
   - Secrets management
   - Module system integration
   - Custom packages/overlays
   - Home-manager integration (if used)
2. Identify missing features or workarounds needed

### Step 5: Migration Decision & Documentation (1 hour)
1. Create comparison document with:
   - Lines of code comparison
   - Feature matrix
   - Pros/cons list
   - Migration effort estimate
2. Make go/no-go decision
3. If "go": proceed to Step 6
4. If "no-go": document reasons and close issue

### Step 6: Incremental Migration (if approved)
**Per host: 30min - 1 hour each**
1. Port host configuration to `nixos-unified`
2. Test deployment to that host
3. Monitor for 24-48 hours
4. Port next host
5. Repeat until all hosts migrated

### Step 7: Cleanup (1 hour)
1. Remove `flake-parts` and `colmena` from flake inputs
2. Delete old configuration files
3. Update README with new deployment instructions
4. Clean up unused Nix code

## 4. Files to Modify

### Files to create
- **`flake.nix`** (modified): Add `nixos-unified` input, create parallel outputs
- **`hosts/unified/`** (new): Directory for `nixos-unified` configurations
- **`hosts/unified/common.nix`** (new): Shared configuration module
- **`hosts/unified/<hostname>.nix`** (new): Per-host configuration in unified format
- **`docs/nixos-unified-evaluation.md`** (new): Comparison and evaluation report
- **`docs/DEPLOYMENT.md`** (modified): Updated deployment instructions

### Files to analyze (current setup)
- **`flake.nix`**: Identify current `flake-parts` and `colmena` usage
- **`flake.lock`**: Document current versions
- **`hosts/`** or similar: Current host configurations
- **`modules/`**: Shared NixOS modules
- **`colmena.nix`** or deployment config: Current deployment setup

### Files to remove (post-migration)
- **Old `flake-parts` modules** in `flake.nix`
- **`colmena.nix`** or colmena-specific configuration
- **`flake-parts` specific organization** (e.g., `parts/` directory)

## 5. Testing Strategy

### Build validation
```bash
# Verify flake structure
nix flake show
nix flake check

# Build system configuration
nix build .#nixosConfigurations.<hostname>.config.system.build.toplevel
```

### Deployment testing
```bash
# Test in VM first
nixos-rebuild build-vm --flake .#<hostname>
./result/bin/run-*-vm

# Dry-run deployment
nixos-unified switch --flake . --dry-run

# Actual deployment (staging first)
nixos-unified switch --flake . --target <staging-host>
```

### Rollback testing
```bash
# Verify rollback capabilities
nixos-unified list-generations
nixos-unified rollback
```

### Validation checklist
- [ ] All hosts build successfully
- [ ] Deployment completes without errors
- [ ] Services start correctly post-deployment
- [ ] Secrets are properly handled
- [ ] Network configuration is correct
- [ ] System boots successfully after deployment
- [ ] Rollback mechanism works
- [ ] Build times are comparable or better

## 6. Risks

### High severity
1. **Deployment failure on production hosts**
   - Mitigation: Test on VMs and staging hosts first; keep rescue images ready
2. **Feature gaps in `nixos-unified`**
   - Mitigation: Complete feature audit in Step 4 before committing to migration
3. **Data loss during secrets migration**
   - Mitigation: Backup all secrets; test secrets access before deployment

### Medium severity
1. **Increased build times**
   - Mitigation: Measure and compare build times during evaluation
2. **Learning curve for team members**
   - Mitigation: Create clear documentation and examples
3. **Incompatibility with existing modules**
   - Mitigation: Audit all custom modules during feature parity check

### Low severity
1. **Need to update CI/CD pipelines**
   - Mitigation: Identify CI integration points early
2. **Documentation becomes outdated**
   - Mitigation: Update docs incrementally during migration
3. **Community support differences**
   - Mitigation: Join `nixos-unified` community channels before starting

### Unknown blockers
- Undocumented behavior differences between tools
- Edge cases in complex multi-host setups
- Performance characteristics under load
- Interaction with other Nix tooling (cachix, nix-direnv, etc.)

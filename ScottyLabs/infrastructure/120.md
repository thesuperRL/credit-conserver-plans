### Why this matters
- **Official Support**: Moving to the NixOS-maintained module provides better long-term support and integration
- **Consistency**: Aligns with NixOS ecosystem standards and best practices
- **Maintenance**: Reduces custom configuration burden by leveraging upstream module
- **Features**: Access to official module features, security updates, and bug fixes

- Using custom/third-party Forgejo runner configuration
- Blocked waiting for NixOS/nixpkgs PR #529621 to merge

## 6. Risks & Mitigations

### High Risk: Breaking Configuration Changes
**Risk**: New module may have incompatible options schema  
**Mitigation**: 
- Thoroughly review module documentation after PR merge
- Test in development environment first
- Keep rollback configuration ready

### Medium Risk: State/Token Loss
**Risk**: Runner re-registration may be required  
**Mitigation**:
- Backup `/var/lib/forgejo-runner/` before migration
- Have Forgejo admin access ready for re-registration
- Document token generation process

### Medium Risk: Service Downtime
**Risk**: CI/CD unavailable during migration  
**Mitigation**:
- Schedule migration during low-activity period
- Communicate downtime window to users
- Have fallback runner available if possible

### Low Risk: Upstream PR Delays
**Risk**: PR #529621 may not merge or may be delayed  
**Mitigation**:
- Monitor PR regularly for updates
- Engage with PR author/reviewers if stalled
- Consider alternative if abandoned (custom module or stay on current setup)

### Low Risk: Dependency Changes
**Risk**: New module may require additional dependencies  
**Mitigation**:
- Review module's `imports` and dependencies
- Ensure sufficient disk space for new packages
- Test build before applying

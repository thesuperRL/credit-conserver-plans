# Implementation Plan: Manage GitHub IdP in terranix

## 1. Problem Analysis

### What needs to be solved
Currently, GitHub Identity Provider (IdP) configuration for SSO/SAML authentication is not managed as infrastructure-as-code using terranix. This creates several issues:

- **Manual configuration drift**: GitHub IdP settings are configured manually through the GitHub UI, leading to inconsistencies across environments
- **Lack of version control**: No audit trail for IdP configuration changes
- **Difficult disaster recovery**: Cannot easily reproduce IdP configuration if lost
- **No infrastructure parity**: Dev/staging/prod IdP configurations may diverge without tracking

### Why this matters
- **Compliance**: Many organizations require auditable infrastructure changes
- **Reproducibility**: Infrastructure-as-code enables consistent deployments
- **Collaboration**: Team can review IdP changes via pull requests
- **Automation**: Enables automated provisioning of GitHub organizations with proper SSO setup

### Scope
- Configure GitHub SAML SSO settings via Terraform GitHub provider
- Manage IdP metadata and certificates
- Handle sensitive data (certificates, keys) securely
- Document the terranix module structure

## 2. Technical Approach

### Strategy
Use the official Terraform GitHub provider (`integrations/github`) to manage organization SAML SSO settings through terranix (Nix-based Terraform configuration).

### Key decisions

1. **GitHub Provider Resource**: Use `github_organization_settings` resource (available in provider v5.0+) to manage SAML SSO configuration

2. **Terranix module structure**: 
   - Create dedicated `github-idp.nix` module
   - Export reusable function that accepts IdP parameters
   - Keep secrets external (reference from environment or secret management)

3. **Secret management**:
   - Store SAML certificates/keys in external secret store (e.g., SOPS, Vault, AWS Secrets Manager)
   - Reference secrets via Terraform data sources or variables
   - Never commit secrets to version control

4. **State management**:
   - Use remote Terraform state backend
   - Enable state locking to prevent concurrent modifications
   - Encrypt state at rest (contains sensitive org settings)

## 3. Implementation Steps

### Step 1: Add GitHub provider to terranix configuration
- Add `integrations/github` provider to terranix providers list
- Configure provider authentication (GitHub App or PAT with `admin:org` scope)
- Set appropriate provider version constraint (≥ v5.0)

### Step 2: Create github-idp.nix module
- Define terranix module file `modules/github-idp.nix`
- Create function accepting parameters: `{ org, ssoUrl, entityId, certificatePath, ... }`
- Return terranix resource configuration for `github_organization_settings`

### Step 3: Configure SAML SSO resource
- Define `github_organization_settings` resource
- Configure SAML SSO enabled flag
- Set SSO URL, entity ID, certificate from parameters
- Configure optional settings (sign-on URL, logout URL)

### Step 4: Integrate secret management
- Add SOPS/Vault data source for SAML certificate
- Reference secret in resource configuration
- Document secret rotation procedure

### Step 5: Test and validate
- Apply to test GitHub organization first
- Verify SSO login flow works
- Check GitHub audit log for changes
- Document rollback procedure

### Step 6: Documentation
- Add README.md to module with usage examples
- Document required GitHub permissions
- Provide troubleshooting guide
- Include secret rotation instructions

## 5. Testing Strategy

### Unit-level validation
1. **Nix evaluation**: Run `nix eval .#terraformConfiguration` to ensure terranix config evaluates without errors
2. **Terraform plan**: Run `terraform plan` to validate generated HCL and provider API calls
3. **Syntax validation**: Use `terraform validate` on generated config

### Integration testing
1. **Test organization setup**:
   - Create dedicated test GitHub organization
   - Apply terranix configuration
   - Verify organization settings in GitHub UI
   - Test SSO login flow with test user

2. **Idempotency check**:
   - Run `terraform apply` twice
   - Second apply should show no changes
   - Validates configuration is complete and stable

3. **State drift detection**:
   - Manually change setting in GitHub UI
   - Run `terraform plan`
   - Should detect drift and offer to correct
   - Validates monitoring capability

### Rollback testing
1. Comment out IdP configuration
2. Apply to disable SSO
3. Verify organization returns to non-SSO state
4. Re-enable to test recovery

### Security verification
- Confirm certificates are not in git history: `git log -p | grep -i "BEGIN CERTIFICATE"`
- Verify state encryption is enabled
- Check Terraform plan output doesn't leak secrets
- Validate least-privilege GitHub token permissions

## 6. Risks

### Technical risks

**Risk 1: GitHub API limitations**
- GitHub provider may not expose all SAML settings via API
- **Mitigation**: Review provider documentation early, identify gaps, document manual steps if needed

**Risk 2: State contains sensitive data**
- Terraform state will contain IdP configuration including certificate metadata
- **Mitigation**: Enforce remote backend with encryption at rest, restrict state access via IAM

**Risk 3: SSO misconfiguration lockout**
- Incorrect IdP settings could lock admins out of organization
- **Mitigation**: Test on non-production org first, maintain backup admin account outside SSO, have rollback plan ready

**Risk 4: Certificate expiration**
- SAML certificates expire and require rotation
- **Mitigation**: Document rotation procedure, set calendar reminders, consider monitoring certificate expiration dates

### Operational risks

**Risk 5: Manual drift**
- Admins may change settings in GitHub UI, creating state drift
- **Mitigation**: Run `terraform plan` in CI periodically to detect drift, educate team on IaC workflow

**Risk 6: Provider version compatibility**
- GitHub provider API may change breaking behavior
- **Mitigation**: Pin provider version, test upgrades in non-prod first, review changelog before upgrading
